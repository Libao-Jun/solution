## 一、App 的本质：按开发技术的类型划分

> 这是全篇**最重要的分类框架**（源自阮一峰概念篇）。搞不清 App 的类型，技术选型、成本评估、上架策略全部无从谈起。

### 1.1 按开发技术划分：App 的三大类

表面上看，手机 App 都是"点击图标就能运行"的应用程序，但它们的**底层技术并不一样**。按**开发技术**，App 可以分成**三大类**：

| #   | 类型         | 英文                            | 一句话本质                                       |
| --- | ------------ | ------------------------------- | ------------------------------------------------ |
| ①   | **原生应用** | native application / native App | 为特定平台用官方技术开发，**无法在其他平台运行** |
| ②   | **Web 应用** | web application / Web App       | 用网页技术做，**必须在浏览器中使用**             |
| ③   | **混合应用** | hybrid application / hybrid App | **原生外壳 + 网页内核**，原生与 Web 结合         |

```text
     Native Apps            Web Apps             Hybrid Apps
   ┌────────────┐        ┌────────────┐        ┌────────────┐
   │  平台专属   │   VS   │  浏览器中   │   VS   │  原生外壳   │
   │  性能最好   │        │  跨平台免装 │        │ + 网页内核  │
   └────────────┘        └────────────┘        └────────────┘
     苹果 / 安卓徽标         浏览器 + 网页           HTML5 徽标
```

> 这三类 App 的**技术模型都不一样，各有优缺点**。企业一般会**选择其中一种作为主要技术栈**，来构建自己的手机 App。
>
> ⚠️ **真正理解 H5 开发，需要先搞清楚什么是原生 App、什么是 Web App，因为混合 App 是在它们的基础上诞生的。** 下面 1.3 / 1.4 / 1.5 三节分别详解这三类。

### 1.2 六类形态总览对比表

| 类型                                     | 核心技术                                         | 运行载体                      | 代表                           | 优点                                                 | 缺点                                                         |
| ---------------------------------------- | ------------------------------------------------ | ----------------------------- | ------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------ |
| **原生 App**（Native）                   | iOS：Swift / Objective-C；Android：Kotlin / Java | 操作系统直接运行              | 微信、抖音、淘宝               | 性能与体验最好，可用**全部**硬件/系统 API            | 成本高（每平台一套团队），必须下载安装，更新需重新安装       |
| **Web App**                              | HTML + CSS + JavaScript                          | 浏览器                        | 各类 H5 站点                   | 免安装、永远最新版、发布无需商店审核、被搜索引擎收录 | Web API 有限、性能差、入口不便（用户需记网址/书签）          |
| **混合 App**（Hybrid / 国内俗称 **H5**） | Web 技术 + 原生容器                              | 原生外壳 + WebView            | Cordova/Ionic/Capacitor 打的包 | 跨平台（一套页面多端）、开发快、成本低、**可热更新** | 有 WebView 中间层，性能不及原生，无法使用平台专有特性        |
| **PWA**（渐进式 Web App）                | Web 技术 + Service Worker + Manifest             | 浏览器（可添加到首屏）        | Twitter Lite、各家 Lite 版     | 可离线、可生成桌面图标、可推送、体验接近原生         | **必须先访问一次网站**才生成图标、iOS 支持不理想、生态案例少 |
| **小程序 / 快应用**                      | 各平台自研语法（本质是**面向特定容器的 H5**）    | 宿主 App（微信/支付宝/抖音…） | 微信小程序、快应用             | 免安装、有流量入口、可直接调宿主能力（支付等）       | 受平台规则限制、无法脱离宿主、包体与能力受限                 |
| **跨平台（编译型）**                     | Flutter(Dart)/RN(JS)/Xamarin(C#)/KMP(Kotlin)     | 编译产物仍是**原生 App**      | Flutter 系 App、RN 系 App      | 一套代码多端、性能接近原生                           | 生态/原生桥接有门槛、双端一致性仍需调试                      |

> **一句话记忆**：**原生**是"本地人"、**Web** 是"网页"、**Hybrid** 是"原生壳 + 网页芯"、**跨平台**是"一套源码编译成原生"。

### 1.3 原生 App（native App）详解

| 维度     | 说明                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **概念** | 专门为特定手机平台开发的应用程序，**无法在其他平台运行**；要同时支持 iOS 和安卓，就必须各写一个                                    |
| **历史** | 与智能手机系统一同诞生——**2007 年 6 月 iPhone 诞生、2008 年 9 月安卓诞生**，同时发布各自的开发方法                                 |
| **语言** | 使用与手机操作系统相同的语言：**iOS 用 Objective-C 或 Swift；安卓用 Java 或 Kotlin**。因与底层系统语言、技术模型一致，性能与体验好 |

**优点**

1. 拥有**较好的性能和体验**。
2. 可以使用系统的**所有硬件和软件 API**——GPS、摄像头、麦克风、加速计、通知推送等，能充分发挥系统潜力。

**缺点**

1. **成本高**：每个平台都要建独立开发团队（大公司一般 iOS、安卓各一个团队）；若出现第三平台（如早期 Windows Phone，也许将来华为鸿蒙 OS），成本更高。
2. 使用底层操作系统的**编译型语言**，开发和调试成本较高，时间周期长。
3. 必须**下载安装**才能使用，升级版本必须重新下载安装；用户往往不愿更新，**厂商被迫长期支持旧版本**。

> **典型场景**：高频使用、重交互、强体验的产品（微信、抖音、淘宝）。

### 1.4 Web App 详解

| 维度     | 说明                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **概念** | 使用网页做的应用程序，**必须在浏览器中使用**；主要技术是 HTML、JavaScript、CSS                                                        |
| **由来** | **2008 年 W3C 发布 HTML 第 5 版（HTML5）**，大幅增强网页功能，使网页可以当作应用程序使用、而不只是展示文字图片——这就是 Web App 的由来 |

**优点**

1. **不需要下载安装**，打开浏览器就能用，**总是使用最新版本**。
2. 开发者写起来快、调试容易、**不需要应用商店批准**就能发布。

**缺点**

1. **Web API 很有限**（目前只有相机、GPS、电池等少数几个），大部分系统硬件不能通过网页访问，也无法直接读取硬盘文件——**无法充分利用平台硬件**。
2. 网页通过浏览器渲染，**性能不如原生 App**，不适合性能要求较高的页面。

**劣势（致命的一点）**：需要打开浏览器使用，用户必须记住如何导航到它（输入网址或翻找书签），**进入远不如原生 App 方便**——这点很致命，事实表明用户偏好原生 App。

> **典型场景**：小公司 / 内容型产品（成本低、覆盖广、可被搜索引擎收录），否则容易变成"僵尸 App"。

### 1.5 混合 App（hybrid App）详解

| 维度     | 说明                                                                                                                                     |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **概念** | **原生 App 与 Web App 的结合：壳是原生 App，里面放的是网页**。可以理解为它内部隐藏了一个浏览器，用户看到的是这个隐藏浏览器渲染出来的网页 |
| **容器** | 原生外壳称为 **"容器"**；内部隐藏的浏览器通常使用系统提供的网页渲染控件（即 **WebView 控件**），也可以自己内置一个浏览器内核             |

**优点（三点）**

1. **跨平台**：Web 技术跨平台，只写一次页面就能支持多个平台；混合 App 只需一个团队，**开发成本较低**。
2. **灵活性**：很容易集成多种功能——易加载外部 H5 页面实现 App 的插件结构；Web 页面也可方便地调用外部 Web 服务。
3. **开发方便**：Web 页面的调试和构建远比原生控件简单省时；页面更新容易（**在服务器上发布新版本，触发容器内更新**）；Web 开发人员易招聘，传统前端可承担开发任务。

**缺点（两点）**

1. 存在**网页引擎中间层**，性能比较欠缺：不如原生 App，而且由于 **WebView 不是全功能浏览器**，可能**比 Web App 都要慢一些**。
2. 页面跨平台，**无法使用只有特定平台提供的功能**，体验不如纯原生。例：早期安卓有物理后退按钮、iPhone 没有，页面设计不得不考虑这一点（安卓页面上自画的后退按钮会与系统后退按钮重复）。

### 1.6 关键澄清：到底什么叫"H5"

**定义**：H5 这个词，可以理解成**就是混合 App 模型**，只不过它**特指混合 App 的前端部分**——因为混合 App 的前端就是 HTML5 网页，所以简称 **H5**。

| 说法       | 正确理解                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------- |
| H5 = HTML5 | ❌ 不准确。H5 在国内前端圈是 **"混合 App 的前端部分"** 的俗称（因为前端就是 HTML5 网页） |
| H5 = 网页  | ❌ 不准确。单纯的网页是 Web App；H5 特指**跑在原生容器里的那层网页**                     |
| 国外怎么说 | 国外**没有"H5"这个词**，直接叫 **Hybrid App**                                            |

### 1.7 混合 App 的三层结构与 JSBridge

混合 App 自上而下分三层：

```text
┌─────────────────────────────┐
│  ① HTML5 网页层（前端页面）  │  ← 前端工程师写这层（Vue/React/原生 JS）
├─────────────────────────────┤
│  ② 网页引擎层（WebView 实例）│  ← 本质是一个隔离的浏览器内核
├─────────────────────────────┤
│  ③ 容器层（原生外壳）        │  ← 原生工程师写这层
└─────────────────────────────┘
```

- **容器**：原生外壳，内部隐藏一个浏览器；能提供**API Bridge**（常以 JavaScript 形式暴露，故称 **JSBridge**），让网页调用底层系统 API（相机、GPS、支付……）。
- **JSBridge 是混合 App 的灵魂**：容器接到网页请求 → 调底层 API → 返回结果给网页。
- **坑点**：不同容器的 API Bridge 不同，为 A 容器写的网页**不能直接放到 B 容器或浏览器**。容器必须跟着平台升级（如 iOS 出新硬件 API，容器要跟进），否则需自己补桥。

### 1.8 PWA：Web App 的增强方案

**PWA（Progressive Web App，渐进式 Web App）** 由谷歌 Chrome 浏览器团队开发，专门针对 Web App 的**三大缺陷**：

1. 不能从手机**首屏直接进入**；
2. 缺乏手机状态栏和锁屏时的**通知推送**能力；
3. 不支持**脱机访问**（断网也能使用）。

**能力**：把网站缓存在手机里供**离线**使用；在**手机首屏生成图标**直接点击进入；具备**通知推送**能力；不带浏览器地址栏和状态栏，体验接近原生 App。

**局限**：**需要先用浏览器访问一次网站**，才能在首屏生成图标；目前 **iOS 系统支持不够理想**；仍属探索性质技术，迄今缺乏足够成功案例。

### 1.9 小程序与快应用：面向特定容器的 H5

- **小程序**可以看作**针对特定容器的 H5 开发**：微信本身是一个容器，开放自己的接口（**JSBridge**），外部开发者使用规定的语法编写页面，容器可以动态加载这些页面。
- 对平台的好处：扩展功能和应用场景、吸引外部开发者、繁荣生态；对开发者的好处：有了**流量入口**，可直接调用宿主各种功能（比如支付）。
- **快应用**：机制与小程序类似，区别是**可以在桌面产生图标**。
- 详见同仓库 [`微信小程序/微信小程序.md`](../微信小程序/微信小程序.md)、[`Taro/Taro.md`](../Taro/Taro.md)。

### 1.10 为什么"用户还是偏好原生"——数据说话

- 谷歌调研各 1000 个原生 App 与 Web App：Web App 覆盖用户更广（1100 万 vs 400 万），但原生 App 用户**使用时长**（188 分钟）远超 Web App（9 分钟）。
- 另一项调研：用户 **87% 的时间花在原生 App，13% 花在 Web App**。
- 但结论并非"Web App 无用"：普通用户每月平均只用 **27 个原生 App**，却会访问 **100 多个手机网站**。**小公司/内容型产品做 Web App 更划算**（成本低、覆盖广、可被搜到），否则容易沦为"僵尸 App"。

> **选型启示**：**高频使用 + 强体验** → 原生/跨平台；**低频访问 + 拉新/展示** → Web/H5。

### 1.11 术语澄清（避免被"高级名词"忽悠）

| 术语                      | 阮一峰概念篇原文是否出现 | 正确理解 / 最接近的表述                                                        |
| ------------------------- | ------------------------ | ------------------------------------------------------------------------------ |
| **原生 / Web / 混合 App** | ✅ 出现                  | 三大类技术模型，各有优缺点，企业选其一作为主要技术栈                           |
| **WebView**               | ✅ 出现                  | 系统提供的网页渲染控件；原文特别强调"WebView 不是全功能浏览器"                 |
| **容器 / 容器层**         | ✅ 出现                  | 原生外壳；混合 App 三层结构的最底层                                            |
| **API Bridge / JSBridge** | ✅ 出现                  | 容器在底层接口与网页之间搭的桥，常以 JavaScript 提供                           |
| **PWA**                   | ✅ 出现                  | 渐进式 Web App，谷歌 Chrome 团队针对 Web App 三大缺陷的方案                    |
| **热更新**                | ❌ 未出现该词            | 相近表述："页面的更新也容易，只要在服务器上发布新版本，触发容器内更新就可以了" |
| **离线包**                | ❌ 未出现该词            | 最接近的表述是 PWA"可以把网站缓存在手机里面，供离线时使用"                     |
| **容器化**                | ❌ 未出现"容器化"        | 原文只有"容器 / 容器层"的概念                                                  |

> 提示：面试/沟通中"热更新""离线包"是业内常用说法，但**它们并非概念篇的原始术语**，不要与"容器 / JSBridge"混为一谈。

## 二、技术栈全景：原生 / 混合 / 跨平台

> 阮一峰技术篇把移动端技术栈严格分为 **3 类**。这是所有选型讨论的基础。

### 2.1 三大技术栈

| 技术栈           | 本质                                  | 代表                                                         | 页面怎么写                        | 学习重点                          |
| ---------------- | ------------------------------------- | ------------------------------------------------------------ | --------------------------------- | --------------------------------- |
| **原生技术栈**   | 平台官方技术                          | iOS: Swift/OC + Xcode；Android: Kotlin/Java + Android Studio | 原生控件                          | 平台 API、控件、生命周期          |
| **混合技术栈**   | **Web 技术 + 容器技术**               | PhoneGap、Cordova、Ionic、Monaca、Framework7、Capacitor      | HTML5 + CSS + JS                  | 容器提供的 **API Bridge**         |
| **跨平台技术栈** | **纯容器技术**（不用 Web 技术写页面） | React Native、Xamarin、Flutter、NativeScript、KMP            | 自研语法写 UI，**编译成原生控件** | 既有 API Bridge，又要学它的 UI 层 |

> **关键区别**：混合栈的页面**就是网页**（跑在 WebView 里）；跨平台栈的页面**是自己的语法**，编译时**翻译成原生控件/自绘控件**，因此**没有 WebView 的性能包袱**。

### 2.2 关于 WebView 的共性认知

任何"在 App 里显示网页"的场景都需要**网页引擎**，通常用系统自带的 WebView 控件：

| 技术栈 | 与 WebView 的关系                               |
| ------ | ----------------------------------------------- |
| 原生   | 需开发者**手动**把 WebView 放到页面上           |
| 混合   | 页面本身就是网页，**默认**在 WebView 中显示     |
| 跨平台 | 提供 WebView 语法，**编译时替换**为原生 WebView |

| 平台    | WebView                                      | 说明                                                              |
| ------- | -------------------------------------------- | ----------------------------------------------------------------- |
| Android | `android.webkit.WebView`                     | 基于 Chromium（可升级）                                           |
| iOS     | `WKWebView`（新）/ `UIWebView`（旧，已废弃） | 功能接近，WKWebView 性能更好；iOS 上所有浏览器内核实质都是 WebKit |

### 2.3 原生技术栈的关键差异

| 对比项   | Android                                 | iOS                        |
| -------- | --------------------------------------- | -------------------------- |
| 语言     | Kotlin（主推）/ Java                    | Swift（主推）/ Objective-C |
| IDE      | Android Studio                          | Xcode（**仅 macOS**）      |
| UI       | Jetpack Compose / XML + View            | SwiftUI / UIKit            |
| 架构     | MVVM / Clean                            | MVVM / MVC / Clean         |
| 打包格式 | **APK**（国内）/ **AAB**（Google Play） | **IPA**                    |
| 发布渠道 | Google Play + 国内各商店                | App Store                  |
| 推送     | FCM / 国内厂商推送                      | APNs                       |
| 支付     | Google Play Billing / 微信支付宝        | Apple IAP / Apple Pay      |
| 主要难点 | 机型碎片化、权限、备案、软著            | 证书签名、审核、内购规则   |

> ⚠️ **iOS 开发的硬门槛**：Xcode **只能运行在 macOS** 上。没有 Mac 又想上架 App Store，需使用云 Mac / 租用 Mac 构建服务（如 GitHub Actions macOS runner、Codemagic、Bitrise）。

### 2.4 混合技术栈谱系：PhoneGap → Cordova → Ionic

- **PhoneGap**：历史最悠久，**诞生于 2009 年**；**2011 年被 Adobe 收购**，改名 Adobe PhoneGap。
- Adobe 将 PhoneGap 的**核心代码捐给 Apache 基金会**，成为新开源项目 **Apache Cordova**。
- 二者是**两个独立发展的开源项目**，但关系密切，可简单理解为：**Cordova 是 PhoneGap 的内核，PhoneGap 是 Cordova 的发行版**。
- 基于 Cordova 封装的其他框架：**Ionic、Monaca、Framework7** 等（另有 Ionic 团队推出的 **Capacitor**，可视作 Cordova 的现代继任者）。
- **共同点**：都用 Web 技术（HTML5 + CSS + JavaScript）开发页面，再由框架分别打包成 iOS 和安卓安装包。
- **优点**：开发简单、周期短、成本低。**缺点**：功能和性能都很有限。

### 2.5 原生技术栈的开发实例（"在 App 里加载网页"最小示例）

| 平台        | 关键步骤                                                                                                                                                                                                                                                 |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **iOS**     | Xcode 新建项目类型为**单视图 App**；在 `ViewController.swift` 中，启动加载视图时（`loadView()`）新建 WebView 实例，视图加载成功后（`viewDidLoad()`）由 WebView 加载外部网页；点运行按钮弹出 **iPhone 模拟器**；一切正常后即可打包生成 App 二进制安装文件 |
| **Android** | Android Studio 新建项目类型为 **"Empty Activity"**；主要修改 `MainActivity.java`，在生命周期 **`onCreate()`** 生成视图时添加并设置 WebView 实例、加载外部网页；运行前**必须连接真机或安装安卓模拟器**；正常后可打包生成安装文件                          |

> 这两段"加载网页"的最小示例，恰好说明了原生与混合的根本差别：**原生需开发者自己把 WebView 控件放到页面上**，而混合 App 的页面本身就是网页。另注：Swift 文件后缀是 `.swift`（不是 `.swifter`）。

## 三、跨平台框架深度对比与选型决策

### 3.1 主流方案横向对比

| 方案                                  | 语言        | 原理                                      | 优点                                                 | 缺点                                                       | 适合                               |
| ------------------------------------- | ----------- | ----------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------- |
| **Flutter**                           | Dart        | **自绘控件**（Skia 引擎），不依赖原生控件 | UI 表现强、性能好、**双端像素级一致**、动画流畅      | 需学 Dart、包体积较大、原生插件/平台通道有门槛             | 想做**高质量跨平台**、追求一致体验 |
| **React Native**                      | JS / TS     | JS 写 UI，**编译成原生控件**              | 前端友好、React 生态庞大、热更新成熟                 | **原生化不一致**（复杂页面双端差异）、原生依赖与版本问题多 | React 前端、快速迭代               |
| **uni-app**                           | Vue         | 编译到 App / 小程序 / H5                  | 国内生态好、**一套代码覆盖小程序 + App**、中文文档全 | 高复杂 App 性能一般、平台差异仍需处理                      | Vue 前端、要覆盖小程序             |
| **Kotlin Multiplatform (KMP)**        | Kotlin      | **共享业务逻辑**，UI 各平台原生           | 共享逻辑、保留原生体验、渐进式                       | 学习成本高、UI 层仍需各写                                  | 原生团队 / 大型团队                |
| **Xamarin / .NET MAUI**               | C#          | 编译成原生控件                            | C# 生态、微软支持、Visual Studio                     | 国内生态与人才较少、包体积较大                             | .NET 团队                          |
| **NativeScript**                      | JS          | 编译成原生控件（基于 Angular 模型）       | 直连原生 API                                         | 生态小于 RN                                                | Angular 团队                       |
| **Hybrid（Cordova/Capacitor/Ionic）** | HTML/CSS/JS | WebView + JSBridge                        | 迭代快、成本最低、可热更新                           | **性能和体验受限**                                         | 活动页、内容页、后台管理系统       |
| **Taro**                              | React/Vue   | 编译到小程序 / H5 / RN                    | 多端统一、React 语法                                 | 多端适配成本                                               | 已有 React 团队做多端              |

### 3.2 选型决策树（前端开发者视角）

```text
你的团队/技术底色是什么？
├─ 会 React / React Native 生态 → RN（快速）或 Expo
├─ 会 Vue → uni-app（要覆盖小程序）或 Ionic/Capacitor（纯 H5 壳）
├─ 无前端包袱、追求体验一致 → Flutter
├─ 已有原生团队、只想共享逻辑 → KMP
└─ 只做展示页/活动页，预算极低 → Hybrid（WebView + Vue/React）

项目诉求是什么？
├─ 性能与体验要求高、预算充足、大型 App → 原生（Kotlin/Compose、Swift/SwiftUI）
├─ 一个团队要覆盖双端 → 跨平台（Flutter / RN）
├─ 要同时覆盖小程序 + App → uni-app / Taro
└─ 只要快速拉新、内容展示 → Web App / H5 / PWA
```

### 3.3 经典选型结论（阮一峰原文总结）

1. **原生技术栈**：技能和体验最好。**复杂的大型 App，条件允许应优先原生。**
2. **混合技术栈**：成本低、灵活性好。**性能要求不高的简单/展示型 App** 可采用。
3. **跨平台技术栈**：适合**只有一个团队、又要跨平台**的情况，但需承担双端一致性、生态成熟度与**审核政策**的风险。

### 3.4 跨平台的历史教训（避坑必读）

- **RN 的双端不一致**：UI 抽象层翻译出的 iOS/Android 原生页面**做不到完全一致**，一个平台正常、另一个出现奇怪小毛病；想做好需**同时精通 RN + iOS + Android 三端**，对开发者要求过高。**Airbnb 用 RN 两年后宣布放弃，回归原生**。
- **Flutter 的取舍**：为**彻底解决 RN 平台差异**，自研一整套控件并打包进 App，因此不存在"调用原生控件不一致"的问题；代价是包体积与平台通道复杂度。
- **Apple 审核风险**：苹果曾在审核指南中**限制"用 H5 等网页技术动态提供核心功能"的 App**（认为应通过 Safari 分发而非 App Store）。纯 H5 壳包上架 App Store 有被拒风险，**核心功能必须原生实现或至少"有意义的使用原生能力"**。

### 3.5 跨平台原理深挖（面试高频）

**React Native 为什么能"既跨平台又接近原生"？**

- **React**（2013 年 Facebook 发布，为网页开发设计）的核心思想：在网页之上建立一个 **UI 抽象层**，所有数据操作都在该层（内存中）完成，再渲染成网页 DOM，从而提升性能。
- 工程师发现这个 UI 抽象层**本质上是一种与底层设备无关的数据结构**：它不仅能渲染成网页，也能渲染成手机原生页面。于是"写一次 React 页面 → 分别编译成 iOS 和安卓原生 App"，这就是 React Native 的由来。
- **关键澄清**：RN 虽然用 JavaScript、写法像 Web 页面，但**所有控件都是它自己定义的**，编译时**一一翻译为对应的原生控件**。例：文本控件 `<Text>` → iOS 的 `UIView`、安卓的 `TextView`。既保证性能又跨平台，因此一诞生就成为热门技术。
- **NativeScript**：与 RN 很像（也用 JavaScript、也编译成原生控件），但开发模型基于 **Angular.js** 而非 React。

**Flutter 为什么能"双端完全一致"？**

- 谷歌为**解决 RN 的平台差异问题**，采用**完全不同的方案**：**自己实现了一整套控件**，打包时把这套控件打包进每一个 App，因此**不存在调用原生控件的问题**——不管什么平台都调用内嵌的自有控件，从而做到 iOS 与安卓体验完全一致。
- 核心代码使用 **Dart** 语言：官方语言，**接近 JavaScript 语法，但多了静态类型支持**。
- 原文撰写时（2019）的局限：历史不长、应用不广泛、API 未稳定——但很值得关注。

**Xamarin**：微软的跨平台框架，原理与 RN 很相似，**语言是 C#**，需配合 **Visual Studio**；WebView 用法与原生很像（先新建控件实例，再放到布局上）。

> 📌 **时效提醒**：以上原理性结论长期有效，但各框架版本迭代很快（RN 新架构、Expo、Flutter 3.x+ 稳定化等），**具体能力与版本状态请以官方最新文档为准**。

### 4.1 前端通用基础

| 领域       | 必须掌握                                                         |
| ---------- | ---------------------------------------------------------------- |
| HTML / CSS | 盒模型、Flex、Grid、定位、媒体查询、动画过渡                     |
| JavaScript | ES6+（解构、Promise、async/await、模块化）、事件循环、闭包、原型 |

| 构建工具   | Vite / Webpack / Gradle / Xcode 构建系统基本概念                 |
| 版本控制   | **Git**（分支策略、合并、冲突解决），团队协作底线                |

### 4.2 移动端特有的概念（Web 开发者最容易踩坑）

| 概念              | 含义 / 为什么要懂                                                                                     |
| ----------------- | ----------------------------------------------------------------------------------------------------- |
| **机型碎片化**    | Android 品牌、屏幕尺寸、系统版本极其分散，必须做兼容适配                                              |
| **屏幕适配**      | 逻辑像素 vs 物理像素、**DPR**（设备像素比）、**安全区**（刘海屏/挖孔屏）、状态栏、底部 Home Indicator |
| **单位体系**      | Android 用 `dp/sp`；iOS 用 `pt`；小程序用 `rpx`；Web 常用 `vw/vh/rem`                                 |
| **1px 边框问题**  | 高清屏上 CSS `1px` 会被渲染成多物理像素，需用 `transform: scaleY(0.5)` 等方案                         |
| **软键盘**        | 弹出会顶起布局、遮挡输入框，需监听并做滚动/占位处理                                                   |
| **返回键 / 手势** | Android 有物理/手势返回，iOS 有侧滑返回；**不能假设只有一种返回方式**                                 |
| **生命周期**      | 前台/后台切换、进程被杀、冷启动 vs 热启动                                                             |
| **权限模型**      | 相机、相册、定位、麦克风、蓝牙、通知、文件——**运行时申请**且用户可拒绝                                |
| **弱网与断网**    | 移动网络不稳定，必须处理超时、重试、离线态、加载态                                                    |
| **电量与流量**    | 移动端用户敏感，轮询/长连接/大图必须优化                                                              |

### 4.3 移动端适配核心要点

## 五、从 0 到 1：完整项目开发流程（17 步）

> 这是**"App 从开发到上架的整个流程"**的标准骨架。

```text
 1. 需求分析       →  2. 原型设计      →  3. UI 设计
 4. 技术选型       →  5. 搭建项目      →  6. 开发页面
 7. 封装网络请求   →  8. 登录注册      →  9. 状态管理
10. 本地存储       → 11. 权限处理      → 12. 接入推送/支付/地图/相机
13. 真机测试       → 14. 性能优化      → 15. 打包
16. 应用市场上架   → 17. 后续版本迭代
```

### 阶段一：需求与设计（1–3）

| 步骤         | 产出物                   | 关键点                                                                                                                                        |
| ------------ | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **需求分析** | PRD（产品需求文档）      | 明确：目标用户、核心功能、是否需登录/支付/定位/推送、是否需后端管理、是否双端、上架渠道（国内 / Google Play）；**功能优先级（MVP 先做什么）** |
| **原型设计** | 交互原型（线框）         | 用 Figma/墨刀画出页面跳转与交互流程；**先确认流程再画视觉**，避免返工                                                                         |
| **UI 设计**  | 设计稿 + 切图 + 设计规范 | 统一色彩/字号/间距/圆角规范；输出多倍图；标注间距与状态                                                                                       |

### 阶段二：开发（4–12）

| 步骤                | 关键点                                                                               |
| ------------------- | ------------------------------------------------------------------------------------ |
| **4. 技术选型**     | 按第四节决策树确定原生/跨平台/Hybrid；确定后端方案（自研 / BaaS / 云开发）           |
| **5. 搭建项目**     | 初始化工程、配置多环境（dev/test/prod）、接入 Lint、配置 Git、搭建目录结构与基础架构 |
| **6. 开发页面**     | 启动页、引导页、登录/注册、首页、搜索、列表、详情、个人中心、设置——按模块推进        |

## 八、App 缓存方案（内存 / 网络 / 图片 / 离线缓存）

> **为什么单独成章**：移动端**流量贵、网络差、电量敏感**，缓存是"体验 + 性能 + 成本"的三重杠杆；但缓存用错就是**旧数据、串号、隐私泄露、存储爆炸**。本章把 App 里的缓存分层、分类型讲清楚，并给出失效与安全策略。
>
> 与 [7.3 本地存储分层](#73-本地存储分层) 的区别：**存储**解决"数据放哪儿"，**缓存**解决"数据放多久、什么时候算过期、怎么失效"。

### 8.1 缓存的分层模型（一张图看懂）

```text
用户请求
   │
   ├─① 内存缓存（L1）  ← 最快，进程内，重启即失（LruCache / Map / 图片内存缓存）
   │        未命中 ↓
   ├─② 磁盘缓存（L2）  ← 文件 / SQLite / Room / Core Data / UserDefaults / WebView Cache
   │        未命中 ↓
   └─③ 网络（L3 源）   ← HTTP 缓存（OkHttp / URLCache）+ CDN 边缘缓存 + 服务端缓存（Redis）
```

**四个核心指标**：**命中率**（越高越省）、**新鲜度**（什么时候过期）、**容量**（占多少内存/磁盘）、**一致性**（会不会看到旧数据）。

> 设计原则：**能缓存就缓存，但必须能失效**；**分层缓存，逐层回退**。

### 8.2 缓存的 8 种形态与性能基准

| #   | 形态               | 存储位置 / 载体                              | 访问速度    | 持久性       | 典型用途                     | 失效 / 淘汰策略                  |
| --- | ------------------ | -------------------------------------------- | ----------- | ------------ | ---------------------------- | -------------------------------- |
| 1   | **内存缓存（L1）** | RAM：`LruCache` / `Map` / ViewModel          | **0.1–1ms** | 进程结束即失 | 列表数据、图片、高频访问对象 | LRU 淘汰                         |
| 2   | **键值缓存**       | SharedPreferences / UserDefaults / DataStore | 快          | 重启保留     | 配置、开关、轻量状态、令牌   | 显式清理                         |
| 3   | **文件缓存**       | `cacheDir`、OkHttp DiskCache                 | **10–50ms** | 重启保留     | 接口响应、大 JSON、下载资源  | TTL + 容量上限                   |
| 4   | **数据库缓存**     | Room / SQLite / Core Data                    | **5–15ms**  | 重启保留     | 结构化数据、离线数据         | 版本号 / 时间戳 / 软删除         |
| 5   | **TTL 缓存**       | 内存（条目自带过期时间）                     | 快          | 依赖实现     | 令牌、临时数据               | **到期自动删除**                 |
| 6   | **HTTP 缓存**      | OkHttp `Cache` / `URLCache`                  | 网络级      | 重启保留     | REST API、图片               | `Cache-Control` / `ETag`         |
| 7   | **多级缓存**       | 内存 + 数据库 / 文件组合                     | 综合最优    | 混合         | 高频读 + 离线场景            | 分层 TTL + LRU + 提升            |
| 8   | **统一缓存管理器** | 对以上做统一封装                             | 综合        | 混合         | 大型 App 统一治理            | 统一 `clearAll()` + **级联失效** |

**性能基准（实测参考）**

| 形态       | 访问时间 | 效果                          |
| ---------- | -------- | ----------------------------- |
| 内存缓存   | 0.1–1ms  | 命中率 **90%+**               |
| 数据库缓存 | 5–15ms   | 适合离线场景                  |
| 文件缓存   | 10–50ms  | 处理大数据                    |
| HTTP 缓存  | —        | 减少 **50%~90%** 网络请求     |
| 多级缓存   | 综合     | 命中率 **95%+**，且带回退能力 |

> **提升命中率的关键机制是"缓存提升（Promotion）"**：L2 命中后把数据回填到 L1（`memoryCache.put(key, it)`），下次即可命中内存；`put()` 时同时写入多层，保证各层一致。

### 8.3 HTTP 缓存（最关键、最容易踩坑的一层）

**强缓存**（不发请求，直接读本地）：

| 响应头                     | 含义                                        | 注意                           |
| -------------------------- | ------------------------------------------- | ------------------------------ |
| `Cache-Control: max-age=N` | N 秒内直接用缓存                            | **优先级最高**                 |
| `Cache-Control: no-cache`  | 不是"不缓存"，而是 **每次都要向服务端校验** | 极易误解                       |
| `Cache-Control: no-store`  | **完全不缓存**（用于隐私/敏感响应）         | 真正的"不缓存"                 |
| `Cache-Control: immutable` | 内容永不变化（配合文件名 hash 的静态资源）  | 长缓存首选                     |
| `private` / `public`       | 仅客户端缓存 / 可被 CDN 等共享缓存          | 含用户信息的响应务必 `private` |
| `Expires`                  | 绝对时间（HTTP/1.0 遗留）                   | 优先级低于 `Cache-Control`     |

**协商缓存**（发请求，服务端说"没变"→ 304，省流量）：

| 机制              | 请求头              | 响应头          | 说明                                   |
| ----------------- | ------------------- | --------------- | -------------------------------------- |
| **ETag**          | `If-None-Match`     | `ETag`          | 内容指纹，**优先级高于 Last-Modified** |
| **Last-Modified** | `If-Modified-Since` | `Last-Modified` | 秒级精度，可靠性略低                   |

**实践要点**

- **静态资源**：`Cache-Control: max-age=31536000, immutable` + **文件名 hash**（内容变则 URL 变，天然失效）。
- **接口（HTML/JSON）**：`no-cache`（每次校验）或**短 TTL**，避免看到旧数据。
- **平台落地**：Android → `OkHttp Cache` + `CacheControl` 拦截器；iOS → `URLSession` / `URLCache`；RN/uni-app/Flutter → 各自请求库的 cache 配置。
- ⚠️ **坑**：`no-cache` ≠ 不缓存；`max-age` 不写 → 走启发式缓存，行为不可控。

**OkHttp 落地范式（Android 最常用的客户端覆写）**

```kotlin
// ① 配置磁盘缓存（容量按业务定，示例 10MB）
val client = OkHttpClient.Builder()
    .cache(Cache(File(context.cacheDir, "http_cache"), 10L * 1024 * 1024))
    .addInterceptor { chain ->
        val online = isNetworkAvailable(context)   // ConnectivityManager 判断网络
        val request = chain.request().newBuilder()
            .header("Cache-Control", if (online) {
                // 在线：5 分钟内直接用缓存，到期再校验
                "public, max-age=300"
            } else {
                // 离线：allow 使用一周内的旧缓存（only-if-cached 不回源）
                "public, only-if-cached, max-stale=604800"
            }).build()
        chain.proceed(request)
    }
    .build()
```

> 核心思路：**在线按正常 TTL 走，离线降级为"用旧缓存"**，让 App 在弱网/无网时仍可用。iOS 侧对应 `URLCache` + `URLRequest.cachePolicy`。

### 8.4 数据（接口）缓存策略

| 模式                              | 行为                                             | 适用                          |
| --------------------------------- | ------------------------------------------------ | ----------------------------- |
| **Cache First（先缓存后网络）**   | 先展示缓存，再请求刷新（Stale-While-Revalidate） | **首页/列表**（秒开体验最好） |
| **Network First（先网络后缓存）** | 先请求，失败才读缓存                             | 时效性强的数据（余额、库存）  |
| **Cache Only**                    | 只用缓存                                         | 离线模式                      |
| **Network Only**                  | 不用缓存                                         | 支付、验证码等强一致场景      |

**设计要点**

- **缓存键** = `URL + 参数 + 用户身份`；⚠️ **必须带用户标识，否则多账号串号**。
- **TTL**：不同接口不同时长（配置类 1 天、列表 5 分钟、实时数据不缓存）。
- **缓存版本**：随 `appVersion` / `apiVersion` 变化整体失效（发版后旧结构不兼容）。
- **主动失效**：写操作成功后清除相关缓存（写后清）；下拉刷新强制绕过缓存。
- **增量同步**：用 `updatedAt` 时间戳或 ETag 做增量拉取，减少全量传输。
- ⚠️ **坑**：**退出登录 / 切换账号必须清用户级缓存**；敏感数据不落盘明文。

### 8.5 图片缓存（流量与内存的最大头）

**经典三级缓存**（Android 高频考点）：

```text
内存缓存 LruCache（强引用、按 size 计量，最快）
    ↓ 未命中
磁盘缓存 DiskLruCache / 文件（journal 日志索引，key 用 MD5 作文件名）
    ↓ 未命中
网络（下载后依次写入 磁盘 → 内存）
```

- **LRU（Least Recently Used，最近最少使用）**：缓存将满时淘汰"最近最少被使用"的对象。Android 3.1+ 自带 `LruCache`（内部基于 `LinkedHashMap`，**按占用的 size 而非条数计量**，需重写 `sizeOf()`）；`DiskLruCache` **不属于 SDK**，需额外引入。
- **Glide 的三级体系**：**活动资源**（正在被 View 使用的图片，弱引用持有）→ **内存缓存 LruCache** → **磁盘缓存**；可用 `skipMemoryCache()` / `diskCacheStrategy()` 精细控制。
- **Fresco** 更进一步：把图片放在 **Ashmem 匿名共享内存**（堆外），显著降低 Java 堆 OOM 风险（代价是接入改造大）。
- **Bitmap 内存管理**：`inSampleSize` 采样、`inBitmap` 复用、及时回收，避免大图 OOM。

| 技术栈       | 推荐库                                     |
| ------------ | ------------------------------------------ |
| Android      | **Coil**（Compose 首选）/ Glide / Fresco   |
| iOS          | **SDWebImage** / Kingfisher / `AsyncImage` |
| React Native | react-native-fast-image / expo-image       |
| Flutter      | cached_network_image                       |
| H5/uni-app   | 浏览器缓存 + CDN 裁剪参数                  |

**优化要点**：**按显示尺寸裁剪**（别把 4000px 原图加载进 100px 的框）、优先 **WebP/AVIF**、列表项复用 + 取消不可见请求、设置内存上限与磁盘上限、预加载首屏关键图。

> ⚠️ **经典坑**：图片 URL 不变 → 换了图仍显示旧图。**解法**：URL 加版本参数 / 内容 hash，或更新后清对应缓存。

### 8.6 WebView / H5 缓存与离线包

- **WebView 自带 HTTP 缓存**：Android `WebSettings.setCacheMode`；iOS 用 `NSURLRequest.cachePolicy`。

| CacheMode                 | 行为                           | 适用     |
| ------------------------- | ------------------------------ | -------- |
| `LOAD_DEFAULT`            | 按 HTTP 缓存头自行决定         | 默认     |
| `LOAD_CACHE_ELSE_NETWORK` | **优先用缓存**，无缓存才走网络 | 离线优先 |
| `LOAD_NO_CACHE`           | 不使用缓存                     | 强一致   |
| `LOAD_CACHE_ONLY`         | 只用缓存                       | 纯离线   |

- **清理相关 API（登出/清缓存必须调）**：`webView.clearCache(true)`（清 HTTP 缓存）、`WebStorage.getInstance().deleteAllData()`（清 LocalStorage/IndexedDB）、`CookieManager.getInstance().removeAllCookies()`（清 Cookie，**防串号**）。
- **离线包**：把 H5 资源（HTML/JS/CSS/图）**预置到 App 本地**，更新时只下发**差量**；需版本管理 + 完整性校验 + 失败回滚。
- **Service Worker（PWA）**：用 Cache Storage 缓存资源，配合版本号在 `activate` 阶段清理旧缓存。
- `AppCache` **已废弃**，不要再用。
- ⚠️ **坑**：WebView 缓存目录**可能含登录态 / Cookie**，**退出登录必须清理**，否则串号；缓存目录无上限会撑爆存储。

### 8.7 离线缓存与数据同步

| 项         | 做法                                                |
| ---------- | --------------------------------------------------- |
| 本地存储   | Room / Core Data / SQLite 存业务数据                |
| 待同步队列 | 操作入队 → 网络恢复后按序提交                       |
| 冲突解决   | 以服务端为准 / 时间戳（LWW）/ 业务字段级合并        |
| 软删除     | 用 `deletedAt` 标记，避免多端"删了又回来"           |
| 同步时机   | App 启动、网络恢复、定时、手动下拉                  |
| 幂等       | 每条操作带唯一 ID，服务端去重，防重复提交           |
| ⚠️ 坑      | 多端并发冲突、设备时钟不准、同步风暴（限流 + 合并） |

### 8.8 缓存的失效与一致性

- **失效手段**：TTL 过期、版本号失效、主动清理（写后清）、LRU/LFU 淘汰、容量上限、**级联失效**。
- **一致性模型**：强一致（少见，代价高） vs **最终一致**（绝大多数 App 采用）。
- **触发全量清理的时机**：App **升级**、**退出登录 / 切换账号**、用户**手动清缓存**、磁盘空间不足。
- **服务端侧相关概念**：缓存**雪崩**（大量 key 同时过期 → 加随机 TTL）、缓存**穿透**（查不存在的数据 → 空值缓存 / 布隆过滤器）、缓存**击穿**（热点 key 失效 → 互斥锁/逻辑过期）。

**① TTL 自动过期（最常用的失效方式）**

```kotlin
data class CacheEntry<T>(val data: T, val timestamp: Long, val ttl: Long) {
    fun isExpired() = System.currentTimeMillis() - timestamp > ttl
}
// get() 时检查 isExpired()，过期即 remove；另有 cleanExpired() 定期批量清理
// 不同条目可配不同 TTL（如 token 1 小时、配置 1 天、列表 5 分钟）
```

**② 级联失效（防止脏读的关键）**

- 一个业务实体会派生多个缓存 key（如 `user_`、`user_profile_`、`user_settings_`）。**更新/登出时按前缀一次性失效**，避免"改了主数据、关联数据还是旧的"。
- 示例：`invalidateUserData(userId)` → 移除该用户所有相关 key。

**③ 数据库层过期清理（后台协程执行，勿阻塞主线程）**

```kotlin
// Room：删除超过 24 小时的记录
@Query("DELETE FROM cached_articles WHERE timestamp < :cutoff")
suspend fun deleteOldEntries(cutoff: Long)
```

**④ 一致性的三层保障**

1. **多级同步写入**：`put()` 同时写入内存 / 数据库 / 文件，避免各层数据打架；
2. **失效联动**：级联失效保证关联缓存同步清除；
3. **事务与冲突策略**：数据库用 **ACID** 事务保证完整，`OnConflictStrategy.REPLACE` 处理冲突覆盖。

> **时间戳驱动**：每个缓存条目都带 `timestamp`，它既是"新鲜度判断"的依据，也是"过期删除"的依据——**统一用时间戳，是最省心的缓存治理方式**。

### 8.9 缓存的容量与清理

- **设上限**：内存缓存一般不超过**可用内存的 1/8**；磁盘缓存建议 **100~300MB**（视业务）。
- **淘汰策略**：LRU（最常用）/ LFU / FIFO。
- **提供"清除缓存"入口**（设置页，用户可见），并展示缓存大小。
- **清理时机**：启动清理过期项、退到后台清理、达到阈值触发。

**四种清理触发方式（组合使用）**

| 方式             | 说明                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| **主动清理**     | `CacheManager.clearAll()` 统一清空 内存 / 键值 / 文件 / TTL 各层                                             |
| **内存压力清理** | 监测内存使用率，**超过阈值（如 80%）**时触发 `clearLeastImportantCaches()`：**优先清临时数据、保留用户数据** |
| **系统自动清理** | 文件缓存位于 `context.cacheDir`，系统在存储紧张时可自动清理（**这也是"缓存"要放 cacheDir 的原因**）          |
| **过期清理**     | TTL 的 `cleanExpired()` + 数据库的 `deleteOldEntries()`                                                      |

**清理优先级"黄金法则"（区分"必清 / 慎清 / 保留"）**

| 类别     | 内容                                                                  |
| -------- | --------------------------------------------------------------------- |
| **必清** | 浏览器历史、短视频临时文件、过期下载内容、安装包残留（`.apk`/`.ipa`） |
| **慎清** | 社交聊天图片、游戏进度存档、音乐离线文件（清了会影响体验）            |
| **保留** | 支付类 App 生物识别数据、登录凭证、重要工作文档缓存                   |

> ⚠️ **清理频率别太频繁**：缓存文件在 App 重新运行后会**逐步重建**，过于频繁清理会**增加 I/O 负担**；常规建议 **1~2 个月**清理一次（用户手动清理的场景除外）。
>
> ⚠️ **坑**：**清缓存不要误删用户数据 / 登录态**——必须区分「**缓存**（可随时重建）」与「**用户数据 / 凭证**（不可丢）」。Android 系统的「**清除缓存**」与「**清除数据**」正是这条红线的两个按钮：前者只删临时文件，后者会**移除应用全部个人配置与数据**。

### 8.10 缓存的安全与合规

| 项             | 要求                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------- |
| **敏感数据**   | token、密码、身份证、聊天记录**禁止明文落盘**；用 **Keychain / Android Keystore** 或加密存储 |
| **多账号隔离** | 缓存的用户数据必须按账号隔离，登出即清                                                       |
| **隐私合规**   | 缓存内容涉及个人信息时，遵循最小必要 + 可删除；提供清除入口                                  |
| **防篡改**     | 离线包 / 资源缓存做**签名校验**，防中间人替换                                                |
| **传输安全**   | 走 **HTTPS**，敏感响应加 `Cache-Control: no-store` / `private`                               |

### 8.11 各技术栈缓存方案速查

| 技术栈           | 内存缓存               | 磁盘 / 数据库                         | 图片缓存                | HTTP 缓存                  |
| ---------------- | ---------------------- | ------------------------------------- | ----------------------- | -------------------------- |
| **Android 原生** | `LruCache` / ViewModel | Room / DataStore / File               | Coil / Glide            | OkHttp `Cache` + 拦截器    |
| **iOS 原生**     | `NSCache`              | Core Data / UserDefaults / File       | SDWebImage / Kingfisher | `URLCache` / `URLSession`  |
| **React Native** | 模块内状态 / MMKV      | AsyncStorage / MMKV / SQLite          | fast-image / expo-image | 请求库 cache 配置          |
| **Flutter**      | 变量 / Provider        | `shared_preferences` / Hive / sqflite | cached_network_image    | Dio `cache_interceptor`    |
| **uni-app**      | 页面 / Vuex / Pinia    | `uni.setStorage` / SQLite             | 自带 `image` 缓存       | `uni.request` + 离线包     |
| **Web / H5**     | JS 变量 / Map          | IndexedDB / localStorage              | 浏览器缓存              | HTTP 缓存 + Service Worker |

### 8.12 缓存踩坑清单（对照自查）

- [ ] 页面总显示**旧数据**（强缓存过头 / URL 不变）→ 用 hash 文件名或短 TTL
- [ ] **退出登录后还能看到上个账号的数据** → 用户级缓存按账号隔离并登出清理
- [ ] 图片换了**不生效** → URL 加版本参数或清对应缓存
- [ ] 缓存**无限增长**撑爆存储 → 设容量上限 + LRU
- [ ] WebView 缓存**带 Cookie 导致串号** → 登出清理 WebView 缓存
- [ ] 误以为 `no-cache` 是"不缓存" → 它只是"每次校验"
- [ ] **清缓存把用户数据/登录态也清了** → 严格区分缓存与用户数据
- [ ] 离线数据与服务端**冲突** → 明确冲突解决策略 + 幂等
- [ ] 敏感信息**明文落盘** → Keychain/Keystore 或加密
- [ ] 服务端缓存**雪崩/穿透** → 随机 TTL / 空值缓存 / 布隆过滤器
- [ ] 内存缓存**持有 Activity context 导致内存泄漏** → 一律用 `applicationContext`
- [ ] 多线程并发读写缓存**数据错乱/崩溃** → 用 `ConcurrentHashMap` / `synchronizedMap`（或 `@Synchronized` 保护）
- [ ] **过度缓存**：无上限、用随机 UUID 当 key 缓存一切 → 必须设容量上限 + LRU
- [ ] 清理过于频繁**增加 I/O 负担**，缓存反复重建 → 常规 1~2 个月一次，交给系统 + 阈值触发

## 十二、App 更新方案（版本更新 / 热更新 / 灰度发布）

> **为什么单独成章**：App 一旦上架，"更新能力"就是它的生命线——审核有周期、线上有 bug、运营要赶活动。**没有更新方案的 App，等于上线即定稿。** 本章覆盖：整包更新、应用内更新、增量更新、强制/推荐/静默更新、灰度发布、热更新（热修复）、插件化与动态化，以及**合规红线**。

### 12.1 更新的两个维度：整包更新 vs 资源热更新

| 维度         | 整包更新（全量 / 增量）                     | 资源热更新（热修复 / 动态化）                             |
| ------------ | ------------------------------------------- | --------------------------------------------------------- |
| 更新内容     | 整个 APK / IPA                              | 前端资源（wgt / 离线包）或代码补丁（dex / JS bundle）     |
| 用户感知     | 需下载安装包，覆盖安装或走商店              | 无感，下载后重启即生效                                    |
| 是否需要审核 | **需要**（iOS 必须，国内 Android 市场也要） | **绕过审核**，平台大多排斥                                |
| 生效范围     | 一切改动                                    | 受限（资源、部分代码；**不能改原生 SDK / 新增原生插件**） |
| 合规风险     | 低                                          | **高**（iOS 明确禁止动态下发可执行代码）                  |
| 典型场景     | 功能迭代、大版本                            | 紧急修 bug、运营活动、AB 实验                             |

> 结论：**整包更新是"正路"，热更新是"应急通道"**——用对了提效，用错了下架。

### 12.2 更新方式一：应用商店更新（Store Update）

| 平台        | 做法                   | 说明                                                                                                                                                                            |
| ----------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **iOS**     | **只能跳转 App Store** | App Store 安装包**无法直接更新**；App 内检测到新版本 → 跳详情页 → 用户点"更新"。链接：`itms-apps://itunes.apple.com/cn/app/id{APPID}` 或 `https://apps.apple.com/app/id{APPID}` |
| **Android** | 跳应用市场             | 通用：`market://details?id={包名}`；跳指定商店需查该商店的包名 / scheme 与参数；国内多商店需按渠道分别配置                                                                      |

- **优点**：合规、用户信任度高、系统集成度高（可自动更新）。
- **缺点**：**审核周期不可控**，无法精确控制用户更新时机；国内多商店需逐个维护。

> ⚠️ **iOS 特有坑**：苹果**不允许"强制更新"弹窗**（不允许用户无法使用旧版本、也不允许把用户往 App 外引导）。iOS 上只能"**提示 + 引导跳转**"，且提示必须**可关闭**。

### 12.3 更新方式二：应用内更新（In-App Update）

**Android 官方方案：Google Play In-App Updates（Play Core）**

| 模式                      | 行为                                   | 适用                       |
| ------------------------- | -------------------------------------- | -------------------------- |
| **灵活更新（Flexible）**  | 后台边下边用，下载完成后再提示重启应用 | 非关键更新，不打断用户     |
| **立即更新（Immediate）** | 全屏遮罩，用户必须更新完才能继续使用   | 关键修复（如存在安全漏洞） |

> 限制：**依赖 Google Play 商店分发**，国内无 Google Play 渠道用不了。

**Android 自托管 APK 更新（国内主流）**

流程：检测版本 → 下载 APK → 校验 → 调起系统安装器 → 覆盖安装。

- **前提**：**包名（applicationId）与签名证书必须完全一致**，否则无法覆盖安装（只能卸载重装，用户数据丢失）。
- **Android 8.0+** 需申请"**安装未知应用**"权限（`REQUEST_INSTALL_PACKAGES`），并用 **FileProvider** 暴露安装包 URI。
- 也可**跳浏览器下载**（最省事但体验差）；应用内下载后调 `plus.runtime.install` 体验更好。

### 12.4 更新方式三：全量更新 vs 增量（差量）更新

| 方案                 | 原理                                                                                    | 优点                               | 缺点                                                       |
| -------------------- | --------------------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------- |
| **全量更新**         | 直接下载完整安装包                                                                      | 实现简单、可靠                     | 包大、耗流量、下载慢                                       |
| **增量（差量）更新** | 只下发"新旧版本差异补丁"（`bsdiff` / `ApkDiffPatch` / Tinker 差量），客户端本地合成新包 | **省流量、下载快**（可省 50%~90%） | 需维护**基线版本矩阵**；合成失败要回退全量；iOS 基本不可用 |

> Google Play 的 **AAB** 分发本身就会做**按设备差分**，属于"官方增量"。

### 12.5 更新策略：强制 / 推荐 / 静默 / 分阶段 / 灰度

| 策略                             | 行为                                                    | 适用场景                                     |
| -------------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| **强制更新**                     | 弹窗**不可取消**，不更新无法继续使用                    | 安全漏洞、接口不兼容、协议变更、重大合规整改 |
| **推荐（提示）更新**             | 弹窗可取消，用户可选择"稍后"                            | 常规功能迭代                                 |
| **静默更新**                     | 后台下载，**下次启动生效**，不打扰用户                  | 小版本、资源包                               |
| **灰度发布**                     | 按比例 / 渠道 / 地域 / 用户标签逐步放量，观察指标后全量 | 所有重要版本                                 |
| **分阶段发布（Staged Rollout）** | Google Play 官方按比例放量（如 1% → 5% → 20% → 100%）   | 海外渠道                                     |
| **渠道 / 区域版本**              | 按分发渠道或地域下发不同版本                            | 多渠道、合规差异                             |

**灰度发布的正确姿势**：`1% → 5% → 20% → 50% → 100%`，每一步观察 **崩溃率 / ANR / 核心转化率**，异常立即暂停或回滚。

> **最低支持版本**：服务端维护 `minSupportedVersionCode`，低于该版本的用户强制更新——这是"接口不兼容"时唯一的兜底手段。

### 12.6 远程配置与功能开关（不发版也能"更新"）

严格说这不是"更新包"，但属于**更新体系的另一半**：

- **远程配置 / Feature Flag**：把功能开关、文案、样式、阈值放在服务端，客户端拉取后动态生效。
- **AB 测试**：按用户分桶下发不同配置，对比效果。
- **作用**：**不用发版**就能开 / 关功能、回滚坏功能、做实验——是降低发版风险的第一道防线。
- 注意：**不能借此绕过审核上线新功能**（尤其 iOS）。

### 12.7 热更新（热修复）总览与合规红线

**定义**：App 运行时通过网络下载更新包（代码或资源），**不重新安装**即完成更新。核心价值是**快速修复 Bug、迭代功能、优化资源**，绕过 1–3 天的审核期。

| 类型       | 更新内容                         |
| ---------- | -------------------------------- |
| 代码热更新 | JS/TS、Lua、Dart、dex 等业务逻辑 |
| 资源热更新 | 图片、文案、配置文件等静态资源   |
| 混合热更新 | 代码 + 资源同时更新              |

**主要挑战**：平台限制（iOS 管控严格、Android 兼容复杂）、安全性（包被篡改、恶意代码注入）、兼容性（设备 / 系统差异）、用户体验（下载速度、流量、静默 vs 弹窗）。

**🚨 合规红线（务必牢记）**

| 平台        | 红线                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **iOS**     | **禁止动态下发 / 执行可执行代码**（JSPatch 因严重安全漏洞被 Apple 封禁）。资源更新仅限**非代码资源**，且**不得改变核心功能**；被判"绕过审核"轻则警告、重则下架 |
| **Android** | 相对宽松；但 **Google Play 渠道要求用官方动态功能模块（DFM）**，自定义热更新可能违反政策；国产厂商对未知来源 dex 加载有限制，需适配（64 位、Android 10+）      |

**安全使用热更新的 4 条守则**

1. **上架审核期间不要弹出热更新提示**；
2. 热更新内容**必须走 HTTPS 下载**，避免被三方网络劫持；
3. **不更新违法内容**，不通过热更新破坏商店利益（如 iOS 虚拟支付必须走内购）；
4. 更新包**必须做签名校验**（RSA/SHA256）+ 支持**回滚**。

### 12.8 Android 原生热修复方案对比

| 方案                               | 厂商                                                      | 原理                                               | 特点                                                            |
| ---------------------------------- | --------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| **Tinker**                         | 腾讯                                                      | 生成 **dex 差量补丁**，运行时合并，支持代码 + 资源 | 成熟度高、生态好（Bugly 底层即基于它）；需合成补丁              |
| **AndFix**                         | 阿里                                                      | 基于 ART 的**方法替换**                            | **即时生效、无需重启**；仅支持方法级修改，**不能新增类 / 资源** |
| **Sophix**                         | 阿里（EMAS）                                              | AndFix 的演进，方法替换 + 资源更新                 | 支持 Dalvik/ART；**即时生效 + 冷启动生效**双模式                |
| **Robust**                         | 美团                                                      | 编译期插桩 + 运行时替换                            | 即时生效、兼容性好；需接入构建插件                              |
| **插件化**                         | 阿里 Atlas / 滴滴 VirtualAPK / 360 RePlugin / DroidPlugin | 把模块做成可动态加载的"插件 APK"                   | 能力强但复杂度高、维护成本大                                    |
| **Dynamic Feature Modules（DFM）** | Google 官方                                               | 动态功能模块                                       | **官方支持、合规**；依赖 Google Play 分发                       |

> **选型建议**：成熟省心选 **Tinker / Bugly**；想即时生效且只修方法选 **AndFix / Sophix**；海外 Google Play 渠道优先 **DFM**。

**HarmonyOS（鸿蒙）** 亦有对应能力：`@ohos.update` 提供 **OTA 全量 / 增量更新**，配合热修复实现版本检测、静默更新与强制更新。

### 12.9 iOS 热更新现状

| 方案                      | 状态                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------ |
| **JSPatch**               | ❌ **已废弃**（安全漏洞被 Apple 封禁，仍有下架风险）                                 |
| **原生代码热修复**        | ❌ 基本不可行（AOT 编译 + 平台禁止）                                                 |
| **资源热更新**            | ⚠️ 仅限图片 / 配置等**非代码资源**（如 `NSBundle` 动态替换），**不得改代码逻辑**     |
| **WKWebView 混合方案**    | ✅ 推荐：把部分功能用 H5 实现，更新服务器 H5 资源（**本质是 Web 更新**），合规风险低 |
| **TestFlight / 内测分发** | ✅ 推荐：走官方 Beta 通道，别碰原生热更                                              |

> **结论**：iOS 优先采用 **WebView 混合方案**或 **TestFlight**，**避免原生代码热更新**。

### 12.10 跨平台与 Web 热更新

| 框架                 | 方案                                                                                    | 说明                                                                             |
| -------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **React Native**     | **Microsoft CodePush**（微软开源；原 App Center 服务已退役 → 改用 Expo Updates / 自建） | 业务逻辑打包为 `index.bundle`，动态下载替换；支持灰度、回滚、监控                |
| React Native         | **rn-fetch-blob + 本地加载**                                                            | 自主可控、无三方依赖；需自研版本管理、校验、回滚                                 |
| **Flutter**          | **Shorebird**（商业）/ 字节 **ByteRoad** / Flutter Dynamic（`.dill`）                   | Flutter 默认 AOT 编译成机器码，**热更新难度高**；也可用 **WebView 混合**间接实现 |
| **uni-app / HTML5+** | **wgt 资源升级包**（详见 12.11）                                                        | 下载 wgt 覆盖资源 → `plus.runtime.restart()` 生效                                |
| **小程序**           | 平台自带热更新                                                                          | 小程序天然"无需安装"，版本更新由宿主容器完成                                     |
| **Hybrid / H5**      | **离线包**（预置 + 增量下发）                                                           | 把 H5 资源打包预置到 App，更新时只下发差量                                       |
| **PWA**              | **Service Worker**                                                                      | 拦截请求、缓存新版本，下次打开即新版本                                           |

> 跨平台 / Web 类热更新的共性是：**更新的是 JS / 资源，不属于"动态下发可执行代码"**，因此在 iOS 上相对安全——但仍**不得用于改变核心功能或绕过审核**。

### 12.11 uni-app / HTML5+ 热更新实战（实战参考）

> 前置条件：HBuilderX 1.6.5 起 uni-app 支持生成 App 资源升级包。

**① 生成 wgt 资源升级包**

1. 先更新 `manifest.json` 中的版本号（如 `1.0.0 → 1.0.1` 或 `1.1.0`）；
2. HBuilderX 菜单 → **发行 → 原生 App-制作移动 App 资源升级包**；
3. 生成结束会在**控制台告知升级包输出位置**。

**② 服务端接口约定**

| 请求参数  | 类型   | 说明                                         |
| --------- | ------ | -------------------------------------------- |
| `name`    | String | 客户端读取到的应用名称（便于多应用复用接口） |
| `version` | String | 客户端读取到的版本号                         |

| 返回参数 | 类型    | 说明                                            |
| -------- | ------- | ----------------------------------------------- |
| `update` | Boolean | 是否有更新                                      |
| `wgtUrl` | String  | wgt 包下载地址（热更新用）                      |
| `pkgUrl` | String  | apk/ipa 下载地址或 App Store 地址（整包升级用） |

**服务端版本比较逻辑**（按 `.` 切分后逐段比较）：

```js
// 大版本更新 → 下发整包；小版本更新 → 下发 wgt 资源包
if (currentVersions[0] < resultVersions[0]) {
  result = { update: true, wgtUrl: "", pkgUrl: result.pkgUrl };
} else {
  result = { update: true, wgtUrl: result.wgtUrl, pkgUrl: "" };
}
```

**③ 客户端检测与安装**

```js
// #ifdef APP-PLUS   ← 必须条件编译，否则非 App 环境没有 plus 对象会报错
plus.runtime.getProperty(plus.runtime.appid, function (widgetInfo) {
  uni.request({
    url: "https://www.example.com/update/",
    data: { version: widgetInfo.version, name: widgetInfo.name },
    success: (res) => {
      const data = res.data;
      if (data.update && data.wgtUrl) {
        uni.downloadFile({
          url: data.wgtUrl,
          success: (downloadResult) => {
            if (downloadResult.statusCode === 200) {
              plus.runtime.install(
                downloadResult.tempFilePath,
                { force: false },
                function () {
                  console.log("install success...");
                  plus.runtime.restart(); // 必须重启，否则新内容不生效
                },
              );
            }
          },
        });
      }
    },
  });
});
// #endif
```

**④ 不支持 wgt 热更新的情况（必须整包升级）**

1. **SDK 部分有调整**（如新增 Maps 模块等）；
2. **原生插件有增改**；
3. 老的非自定义组件编译模式下**新增了 nvue 文件**（该模式未打包 weex 引擎，原生引擎无法动态添加）。

**⑤ 注意事项（踩坑高发）**

- 升级检测代码**必须条件编译**（`#ifdef APP-PLUS`），否则非 App 环境报错；
- **`plus.runtime.version` / `uni.getSystemInfo()` 读到的是 apk/ipa 包版本，不是资源版本**——资源版本要用 `plus.runtime.getProperty()` 获取；
- **真机运行基座无法测试升级**（基座版本固定），需打包自定义基座或正式包；
- 安装 wgt 成功后**必须 `plus.runtime.restart()`**；
- 原生引擎不升级、只升级 wgt 时，注意**资源与原生基座的兼容性**；
- 应用中引用的**路径尽量不要包含特殊符号**。

### 12.12 更新包安全与回滚

| 项               | 做法                                                                |
| ---------------- | ------------------------------------------------------------------- |
| **签名校验**     | 更新包用 RSA/SHA256 签名，客户端校验合法性，防篡改 / 中间人         |
| **HTTPS**        | 所有更新请求走 HTTPS                                                |
| **基线版本声明** | 更新包声明支持的基线版本，避免跨版本冲突                            |
| **自动回滚**     | 更新后**崩溃率超阈值（如 5%）自动回滚**（如 CodePush `rollback()`） |
| **断点续传**     | 大包支持断点续传，避免弱网重复下载                                  |
| **降级保护**     | 低配置设备降低更新频率；WiFi 下自动下载、非 WiFi 提示确认           |
| **灰度 + 监控**  | 灰度放量 + 崩溃 / ANR 监控联动，异常即停                            |

### 12.13 更新方案选型速查

```text
要更新什么？
├─ 原生代码 / 新增原生能力 ──────→ 只能整包更新（走商店或自托管 APK）
├─ 前端资源 / JS 业务逻辑 ───────→ 热更新（RN CodePush / uni-app wgt / 离线包）
├─ 仅改开关 / 文案 / 阈值 ───────→ 远程配置（Feature Flag），不发版
└─ 图片 / 配置等静态资源 ────────→ 资源热更新（iOS 也可，但不得改核心功能）

用什么渠道？
├─ iOS ────────────────────────→ 跳 App Store（不可强制）；热更仅限资源 / H5
├─ Android 国内 ───────────────→ 自托管 APK 覆盖安装（包名 + 证书一致）或跳各市场
└─ Android 海外 ───────────────→ Google Play In-App Updates / Staged Rollout / DFM
```

> **一句话总结**：**能走商店就走商店，能配置就不发版，热更新只当"急救包"**——且永远守住 iOS 的合规红线。

### 12.14 更新方案速查清单

- [ ] 服务端维护版本接口（返回 `update` / `wgtUrl` / `pkgUrl` / 更新说明 / 强制标记）
- [ ] 支持**强制更新 / 推荐更新**两种模式，并维护 `minSupportedVersionCode`
- [ ] Android 自托管更新：**包名 + 证书一致**、`REQUEST_INSTALL_PACKAGES`、FileProvider
- [ ] iOS 只做"提示 + 引导"，**不做强制拦截**
- [ ] 更新包**签名校验 + HTTPS + 可回滚**
- [ ] 重要版本走**灰度发布**，观察崩溃率后全量
- [ ] 热更新**不在审核期弹窗**、内容合规、不乱用
- [ ] 版本号（versionCode / versionName）随每次更新**递增**并留档

## 十三、上架全流程（Android / iOS / Google Play / 国内市场）

### 13.1 通用上线流程（Android 视角）

```text
开发完成 → 真机测试 → 隐私合规检查 → 准备应用资料
        → 准备 APP 备案 / 软著 / 特殊资质 → 生成正式签名包
        → 注册开发者账号 → 创建应用 → 上传 APK / AAB → 填写应用信息
        → 填写权限 / 隐私 / 数据安全说明 → 提交审核 → 处理驳回
        → 审核通过 → 正式上线 → 监控崩溃/评论/数据 → 版本迭代
```

### 13.2 上线前资料准备（清单）

| 类别         | 明细                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **基础资料** | 应用名称、包名、图标（常见 512×512）、截图、简介、隐私政策链接、用户协议、测试账号、联系方式、版本号                        |
| **技术资料** | APK/AAB、keystore、applicationId、SHA-1/SHA-256 指纹、target/min SDK、**权限清单**、**第三方 SDK 清单**                     |
| **合规资料** | 隐私政策（必需）、用户协议、**APP 备案**（国内通常需要）、**软件著作权**（国内常见要求）、ICP 备案/许可证、**特殊行业资质** |

### 13.3 开发者账号

| 渠道                | 流程                                                                                    | 费用/周期                   |
| ------------------- | --------------------------------------------------------------------------------------- | --------------------------- |
| Google Play Console | Google 账号 → 个人/组织 → 填资料 → 付费 → 身份验证 → 创建应用（**建议开启两步验证**）   | 一次性注册费                |
| 国内市场            | 华为 AGC、小米、OPPO、vivo、腾讯应用宝：注册 → 实名/开发者认证 → 创建应用 → 上传 → 审核 | 免费，需实名                |
| Apple               | Developer Program                                                                       | 个人 $99/年；公司需 D-U-N-S |

> **企业账号 vs 个人账号**：国内市场企业账号权限更高、推荐权重更高；**金融类、医疗类 App 必须用企业开发者账号**。企业需营业执照、法人身份证、对公账户、授权书、软著等。

### 13.4 各平台审核周期与特点（国内 Android）

| 平台           | 审核周期        | 特点                                     |
| -------------- | --------------- | ---------------------------------------- |
| 华为应用市场   | 3–5 个工作日    | 审核较严，对功能完整性与体验要求高       |
| 小米应用商店   | 2–3 个工作日    | 周期较短，通过率较高                     |
| 应用宝（腾讯） | 1–3 个工作日    | 金融类、社交类审核明显收紧，需更详细资质 |
| OPPO / vivo    | 约 3–5 个工作日 | 标准较统一                               |

**策略建议**：提交前先细读各平台《审核规范》《开发者协议》；**按审核严格程度由高到低依次提交**，用严格平台暴露问题、用宽松平台快速上线。

### 13.5 国内市场素材规格（易被忽略）

| 平台          | 图标规格                   |
| ------------- | -------------------------- |
| 华为应用市场  | 512×512 px，PNG            |
| 小米应用商店  | 1024×1024 px               |
| OPPO 软件商店 | 540×540 px，**背景需透明** |

- 截图通常需 **5 张**，覆盖不同使用场景，多为 **1080×1920 竖图**（以平台要求为准）。
- 需准备**宣传语 / 一句话简介**，符合各平台字数限制。
- **截图不得使用与实际功能不符的诱导性图片**。

### 13.6 Google Play 上架要点

1. 使用 **AAB** 格式上传。
2. 填写**商店详情**：名称、描述、图标、Feature Graphic、截图、分类、隐私政策。
3. 配置 **App Content**：隐私政策 URL、广告、App access、目标受众、内容分级、**Data Safety（数据安全表）**、权限声明、金融/健康/新闻声明。
4. **建议先走测试轨道**：Internal → Closed → Open → Production。
5. **常见驳回**：隐私政策缺失/打不开、Data Safety 与实际不符、权限用途不合理、需登录却没给测试账号、应用崩溃、目标 API 不达标、内容分级不准、侵权、支付违规（数字商品必须用 Play Billing）。

### 13.7 iOS App Store 上架

```text
注册 Apple Developer → 创建 App ID → 配置证书与描述文件
→ Xcode Archive → 上传 App Store Connect → TestFlight 测试
→ 填写信息/截图/隐私 → 提交审核 → 通过后发布
```

**iOS 审核特别注意**：

- 提供**测试账号**（苹果审核员必须能登录体验）。
- 隐私：填写 **Privacy Nutrition Label（隐私标签）**；权限用途描述必须具体。
- **虚拟商品必须走 Apple IAP**，外部支付链接会被拒。
- 提供第三方登录时必须提供 **Sign in with Apple**。
- 拒绝"纯套壳 H5"（核心功能必须有原生能力）。
- 遵守 **App Tracking Transparency (ATT)**：追踪用户需弹窗授权。

### 13.8 审核十大常见问题与解决方向

| #   | 问题                   | 解决方向                                                                 |
| --- | ---------------------- | ------------------------------------------------------------------------ |
| 1   | 隐私政策问题           | HTTPS 链接、**免登录可访问**、App 内有入口、列全 SDK、写清权限用途       |
| 2   | 权限过度申请           | 删无用权限、改为功能触发时申请、Android 13+ 用 Photo Picker              |
| 3   | 测试账号问题           | 提供固定账号密码、避免只支持短信验证码、审核备注写清操作路径             |
| 4   | 崩溃 / 白屏            | 正式包多机型真机测试、检查混淆（ProGuard/R8）、接口 HTTPS 证书、动态权限 |
| 5   | 签名不一致             | 找回原 keystore、区分 upload key / app signing key                       |
| 6   | 版本号问题             | 每次递增 versionCode、建立版本发布记录表                                 |
| 7   | 软著 / 资质问题        | 提前申请软著、主体不一致准备授权书、避免侵权素材                         |
| 8   | APP 备案问题           | 提前提交备案、主体一致、App 内展示备案号                                 |
| 9   | 第三方 SDK 违规        | 升级合规版本、同意后再初始化、关闭非必要采集                             |
| 10  | 图标 / 截图 / 描述问题 | 用真实截图、无水印、避免"最强/稳赚/官方/第一"等夸张词                    |

### 13.9 上线后维护与监控指标

- **更新流程**：收集反馈 → 修复/新增 → 改版本号 → 新正式包 → 内部测试 → 上传 → 填更新说明 → 提交审核 → **灰度发布 → 全量**。
- **监控指标**：崩溃率、ANR、登录成功率、支付成功率、接口错误率、用户评论、卸载率、权限拒绝率、DAU/MAU、留存率。
- **版本更新**：国内市场每次更新都需审核（约 1–3 个工作日），需提供更新说明；**更新过于频繁可能导致审核加严**。

## 十四、合规与法律红线

> 这是**国内上架与海外上架的生死线**，踩中即下架/封号。

### 14.1 隐私合规（最高优先级）

依据：《个人信息保护法》《数据安全法》《网络安全法》，以及各平台审核规范。

| 要求             | 具体做法                                                                             |
| ---------------- | ------------------------------------------------------------------------------------ |
| 隐私政策         | **独立的隐私政策页面 + 独立可访问的 HTTPS URL**；App 内有入口（登录/注册/设置/关于） |
| 内容必须涵盖     | 收集范围（设备信息、位置、通讯录等）、使用目的、数据共享情况、用户权利、安全措施     |
| **首次启动弹窗** | 用户**同意前不得初始化任何敏感 SDK / 采集信息**                                      |
| 第三方 SDK       | 列全（名称、公司、用途、收集字段）；用合规版本                                       |
| 权限             | "能不用就不用、使用时再申请"，拒绝后友好提示                                         |
| 用户权利         | 提供**账号注销、信息删除、撤回授权**入口                                             |
| 未成年人         | 涉及未成年人需额外提供**未成年人保护条款**（如青少年模式）                           |

### 14.2 三大资质（国内）

| 资质                   | 说明                                                                                                           | 周期                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| **APP 备案**           | 工信部要求（2023 年起国内 App/小程序强制备案），通过云服务商或省通信管理局提交；**App 内需展示备案号**         | 需提前准备                    |
| **软件著作权（软著）** | 华为、应用宝**必须提供**；小米、豌豆荚可用**承诺函**替代。**软著名称须与上架名称完全一致**，否则需名称变更证明 | 约 **30–45 天**，建议提前申请 |
| **特殊行业资质**       | 新闻、医疗、金融、教育、游戏（**版号**）、直播、电商、社交等需对应许可证                                       | 差异大，尽早准备              |

> 一份软著可用于多个应用市场，无需重复申请。ICP 备案/许可证按接入情况准备。

### 14.3 其他红线

| 项         | 说明                                                                    |
| ---------- | ----------------------------------------------------------------------- |
| 内容安全   | 不得含违法违规内容；UGC 类需有审核机制                                  |
| 广告合规   | 广告标识、不得诱导点击、开屏广告可关闭                                  |
| 支付合规   | 虚拟商品按平台规则走内购/Billing                                        |
| 数据出境   | 涉及跨境需合规评估                                                      |
| 知识产权   | 素材/字体/音乐/图标避免侵权                                             |
| 签名与密钥 | 保管好，丢失将无法更新已有版本                                          |
| **马甲包** | 用同一 App 换个壳反复上架属**违规**，有被拒审/下架/封号风险，**不建议** |

## 十五、进阶避坑知识（非新人必读）

### 15.1 选型与架构坑

| 坑                   | 说明与规避                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| 盲目上跨平台         | RN 双端不一致、Flutter 原生插件门槛，**大型 App 慎重**；团队只会 Web 技术时，Hybrid 性能要提前评估 |
| 纯 H5 壳上 App Store | 苹果明确限制"网页动态提供核心功能"，**核心功能必须原生**                                           |
| 架构无分层           | 业务与 UI 耦合，后期无法维护；应尽早 MVC/MVVM 分层                                                 |
| 不预留多环境         | 上线后才发现测试/生产地址混乱，应一开始就配多环境                                                  |

### 15.2 工程化坑

| 坑             | 规避                                               |
| -------------- | -------------------------------------------------- |
| 依赖版本不锁定 | RN/Flutter 生态版本冲突多，**锁定版本 + 定期升级** |
| 不接 CI/CD     | 手动打包易出错，接入自动构建与自动上传             |
| 无代码规范     | Lint 未接入、提交混乱，协作成本高                  |
| 单机开发       | 关键模块无评审，缺陷后置                           |

### 15.3 构建与签名坑（致命级）

| 坑                 | 后果                                   | 规避                         |
| ------------------ | -------------------------------------- | ---------------------------- |
| keystore 丢失/泄露 | **无法更新已上线 App**，只能换包名重上 | 多地备份、不入 Git、密码托管 |
| 用 Debug 包上架    | 审核不通过 / 性能差                    | 严格 Release 签名            |
| versionCode 未递增 | 无法覆盖安装/上传被拒                  | 建立版本记录，发版必递增     |
| 包名随意更改       | 视为全新应用，用户流失                 | 上架后不改包名               |
| 混淆未 keep 反射类 | 运行时崩溃                             | 配置 keep 规则并做混淆后测试 |
| 目标 API 未达标    | Google Play 拒审                       | 跟进官方 targetSdk 要求      |

### 15.4 跨平台特有坑

| 框架         | 坑                                                                                |
| ------------ | --------------------------------------------------------------------------------- |
| React Native | 原生模块版本不匹配、`node_modules` 体积、Hermes/新架构迁移、双端样式差异          |
| Flutter      | 包体积、平台通道（Platform Channel）需写原生、插件维护滞后、iOS 需 CocoaPods 环境 |
| uni-app      | 平台差异需条件编译、复杂动画性能、原生插件需花钱/自研                             |
| Hybrid       | JSBridge 版本兼容、WebView 内核差异（Android 各厂商 ROM）、首屏白屏               |

### 15.5 热更新与合规坑

- **热更新**（Hybrid/RN 动态下发 JS、离线包）能绕过商店审核，但**苹果/Google 对此有政策限制**：改变核心功能的热更新会被拒/下架。
- 合规做法：**仅用于修 bug / 小范围调整**，不得用于绕过审核上线新功能。
- Android 侧注意：动态下发可执行代码（DEX/so）在国内市场也受限制。
- **完整方案（整包 / 应用内 / 增量 / 灰度 / 热修复 / 插件化）见 [十二、App 更新方案](#十二app-更新方案版本更新--热更新--灰度发布)。**

### 15.6 网络与安全坑

| 坑                | 规避                                        |
| ----------------- | ------------------------------------------- |
| 明文 HTTP         | 必须 HTTPS；iOS ATS、Android 网络安全配置   |
| 敏感信息明文存储  | 用 Keystore/Keychain                        |
| 无证书校验        | 高安全场景做证书固定（Certificate Pinning） |
| 接口无鉴权/防重放 | 加签名、时间戳、nonce                       |
| WebView 漏洞      | 关闭不必要的 JS 接口、白名单、升级内核      |

### 15.7 上线与运维坑

| 坑             | 规避                        |
| -------------- | --------------------------- |
| 上线无灰度     | 先小流量观察崩溃率再全量    |
| 无崩溃监控     | 接 Crashlytics/Sentry/Bugly |
| 无埋点         | 无法量化版本效果            |
| 未做机型兼容   | 上线后特定机型崩溃/布局错乱 |
| 未处理权限拒绝 | 用户拒绝权限后功能崩溃      |
| 审核备注不清   | 审核员无法复现功能 → 被拒   |

## 十六、App 开发综合注意事项

### 16.1 技术侧

1. **正式包 ≠ Debug 包**：上架必须 Release 正式签名。
2. **包名 / Bundle ID 一旦上架不可改**。
3. **versionCode / CFBundleVersion 每次必递增**。
4. **密钥文件（keystore / 证书）多处备份且不入 Git**。
5. **targetSdk / 目标 API 必须达标**。
6. **混淆后必须回归测试**（反射、序列化、三方 SDK）。
7. **首启不崩溃**是审核最低要求，务必多机型真机测试。
8. **接口全部 HTTPS**，敏感信息安全存储。
9. **权限最小化**，功能触发时再申请。
10. **第三方 SDK 清单完整**，同意隐私政策后再初始化。

### 16.2 合规侧

1. 隐私政策**完整、独立 URL、App 内有入口、免登录可访问**。
2. **首启隐私弹窗**，同意前不采集任何信息。
3. 提供**账号注销、信息删除、撤回授权**入口。
4. 国内提前备好 **APP 备案 + 软著**（+ 特殊行业资质）。
5. 未成年人保护条款 / 青少年模式（如涉及）。
6. 避免使用"最强、第一、官方、稳赚"等**违规绝对化用语**。

### 16.3 商店侧

1. 名称/图标/截图/描述规范，**与实际情况一致**。
2. 分类正确，邮箱可用，链接可访问。
3. **提供可用测试账号**并在备注写清操作路径。
4. 更新说明完整。
5. 学习各平台审核规范，**由严到宽**依次提交。

### 16.4 独立开发者十条红线

> ① 包名不乱改 ② 签名文件保存好 ③ versionCode 递增 ④ 隐私政策完整可访问 ⑤ 权限能少则少 ⑥ 第三方 SDK 列清楚 ⑦ 国内提前备好备案 + 软著 ⑧ Google Play 关注 AAB、Data Safety、目标 API、权限声明 ⑨ 审核前提供可用测试账号 ⑩ 上线后持续监控崩溃、评论、下载与转化。

| versionCode 未递增 | 上传失败         | 发版必递增                  |

| 隐私政策打不开     | 被拒             | HTTPS + 免登录可访问        |
| 首启申请全部权限   | 被拒             | 使用时再申请                |
| 未列第三方 SDK     | 被拒             | 列全并延迟初始化            |
| 无备案 / 软著      | 国内无法上架     | 提前 30–45 天准备           |
| 无测试账号         | 被拒             | 提供固定账号 + 备注路径     |
| 目标 API 未达标    | Google Play 拒审 | 跟进官方要求                |
| 虚拟商品不用内购   | iOS/Play 下架    | 走 Apple IAP / Play Billing |
| 纯 H5 壳包         | App Store 被拒   | 核心功能原生实现            |
| 混淆未 keep        | 崩溃             | 配 keep 规则并回归          |

> **结语**：App 开发的本质是 **"用合适的工具，把需求做成一个能稳定运行、能通过审核、能持续迭代的产品"**。
> 新人先建立**全流程认知**（分类 → 选型 → 开发 → 测试 → 打包 → 上架 → 迭代），老手重点盯**合规红线、签名与版本管理、性能与稳定性**。
