## 一、为什么必须选许可证

**没有许可证的代码 = 保留全部版权，不是开源。**

版权法默认禁止共享：作品一经产生即自动享有版权，他人未经许可不得复制、修改、分发。把源码放到 GitHub 上只是"公开展示"，并不等于授予任何使用权利。所以：

- 仓库里**没有 LICENSE 文件** → 别人只能看，不能用，一用就侵权；
- 想让别人真正能用 → 必须**明确地**附上一份开源许可证。

> 阮一峰原文下的一个经典提问："JavaScript 这样的客户端脚本，不加密就算开源了吧？"
> 回答：**不算**。没有版权说明，就属于保留全部版权，他人只能借鉴，不能直接拿过来用。

许可证解决的是三件事：

1. **授予**：允许他人使用、修改、分发（否则法律默认禁止）；
2. **约束**：在什么条件下允许（保留署名、必须开源、必须提供源码……）；
3. **免责**：不提供担保、不承担使用后果的责任。

## 二、核心概念：三个词决定一切

### 2.1 宽松式（Permissive）vs 著佐权（Copyleft）

| 维度     | 宽松式 Permissive                            | 著佐权 Copyleft                    |
| -------- | -------------------------------------------- | ---------------------------------- |
| 代表     | MIT、BSD、Apache-2.0、ISC、BSL、MulanPSL-2.0 | GPL、AGPL、LGPL、MPL、EPL          |
| 核心区别 | **允许修改后闭源**                           | **修改后的衍生作品必须继续开源**   |
| 主要义务 | 保留版权与许可声明（披露要求）               | 保留声明 + 提供源码 + 同许可证     |
| 典型诉求 | 希望被广泛采用、被商业集成                   | 希望防止被闭源分叉、保护项目完整性 |
| 采用率   | 极高（npm/PyPI 生态主流）                    | 中（基础设施、工具类项目）         |

**Copyleft（著佐权）** 是理查德·斯托曼创造的词，与 Copyright（版权）相对：

- Copyright 直译"复制权"——不经许可，无权复制；
- Copyleft——不经许可，可以随意复制，**但附带前提条件**。

Copyleft 的三个核心条件：

1. 分发二进制格式时，必须提供源码；
2. 修改后的源码，必须与修改前保持许可证一致；
3. 不得在原始许可证之外，附加其他限制。

一句话：**修改后的 Copyleft 代码不得闭源。**

按约束强度从强到弱排序：**AGPL > GPL > LGPL > MPL**（MPL 是文件级弱 copyleft，与 LGPL 侧重点不同）。

### 2.2 分发（Distribution）——触发义务的开关

除 AGPL 外，绝大多数许可证的义务**只在"分发"时才被触发**。

- **分发**：把版权作品从一个人转移到另一个人；
- **不构成分发**：自己使用、公司内部使用（注意这里的"人"也指法人，所以公司内部使用通常不构成分发）；
- **SaaS 不构成分发**：用开源软件对外提供云服务，不分发二进制，因此无需提供源码——**AGPL 是唯一例外**，它规定"网络使用即分发"。

> 这是 AGPL 存在的全部意义：堵住"我把 GPL 软件改改拿去做 SaaS，不分发就不用开源"的漏洞。

### 2.3 专利、商标与担保

| 事项          | 说明                                                                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **专利**      | Apache-2.0、GPLv3、MPL-2.0、EPL 等含**明确的专利授权条款**；BSD、MIT、GPLv2 **未提及专利**，但一般认为默认隐含授予。除非有明确的"保留专利"条款，使用开源软件通常不会构成专利侵权。 |
| **商标**      | 几乎所有许可证都不授予商标权（Apache-2.0、MPL-2.0 等明确排除）。项目名/Logo 的使用需另行授权。                                                                                     |
| **担保/责任** | 所有主流许可证都**明确免责**：不保证代码质量，不承担使用后果。这是正常的，不是"霸王条款"。                                                                                         |

## 三、许可证的三大阵营与全景图

```
开源许可证
├── 公共领域 / 无条件的（Public Domain）
│   └── Unlicense、CC0-1.0、0BSD、MIT-0、WTFPL
│       └── 连"保留署名"都不要，等同于放弃版权
│
├── 宽松式（Permissive）—— 允许闭源
│   ├── MIT（最流行，最短）
│   ├── BSD-2-Clause / BSD-3-Clause / BSD-4-Clause
│   ├── ISC（MIT 的精简版）
│   ├── Apache-2.0（含明确专利授权 + 声明改动）
│   ├── BSL-1.0（仅源码分发需保留声明）
│   ├── MulanPSL-2.0（木兰宽松许可证，中英双语）
│   ├── zlib / PostgreSQL / NCSA / UPL-1.0
│   └── ...
│
└── 著佐权（Copyleft）—— 衍生产物必须开源
    ├── 强 copyleft（项目级）
    │   ├── AGPL-3.0（网络交互即触发）
    │   ├── GPL-2.0 / GPL-3.0
    │   └── EUPL、OSL-3.0、CeCILL
    ├── 弱 copyleft（库级 / 文件级）
    │   ├── LGPL-2.1 / LGPL-3.0（动态链接可豁免）
    │   ├── MPL-2.0（文件级，新增文件可闭源）
    │   └── EPL-1.0 / EPL-2.0、MS-RL
    └── 非标准 / "伪开源"（Source Available）
        ├── SSPL（MongoDB、Elasticsearch）—— OSI 明确声明不是开源许可证
        ├── Elastic License 2.0
        ├── BUSL 1.1（Terraform、HashiCorp 系）
        └── RSALv2（Redis）
```

### 三个阵营对比速览

| 阵营        | 修改后可闭源？          | 需提供源码？ | 需同许可证？ | 典型代表                    |
| ----------- | ----------------------- | ------------ | ------------ | --------------------------- |
| 公共领域    | ✅                      | ❌           | ❌           | Unlicense、CC0              |
| 宽松式      | ✅                      | ❌           | ❌           | MIT、Apache-2.0、BSD        |
| 弱 copyleft | 部分（库/文件外可）     | 被许可部分要 | 被许可部分要 | LGPL、MPL                   |
| 强 copyleft | ❌                      | ✅           | ✅           | GPL、AGPL                   |
| 源码可得    | 通常受限（商用/多租户） | 视条款       | —            | SSPL、BUSL、Elastic License |

## 四、主流许可证

> 下面每种许可证统一用 **「许可 / 条件 / 限制」** 三段式展示，对应 choosealicense.com 的 Permissions / Conditions / Limitations。
>
> - **许可** ✓：授予使用者可以做什么（商业使用、分发、修改、专利使用、私人使用）。
> - **条件** ⓘ：使用者必须遵守什么义务（保留声明、提供源码、同许可证、声明改动、网络使用即分发）。
> - **限制** ✕：许可证明确免责声明或不授予的权利（责任、担保、商标、专利）。

---

### 4.1 宽松式（Permissive）

宽松式许可证的共同点是：**允许修改后闭源**，核心义务基本只有"保留版权与许可声明"； Apache-2.0 等少数还会额外要求"声明改动"或明确"专利授权"。

#### MIT License（SPDX: `MIT`）

| 许可                                             | 条件                 | 限制             |
| :----------------------------------------------- | :------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 保留版权与许可声明 | ✕ 责任<br>✕ 担保 |

**一句话**：最流行、最简短的宽松许可证，只要求保留版权声明，修改后可闭源。专利授权未明示，通常视为隐含授予。

**适合**：个人项目、前端库/框架、小工具、希望最大化传播和复用的代码。MIT 的兼容性几乎最好，可被 GPL/AGPL 项目吸收。  
**代表项目**：React、Vue、Node.js、jQuery、Ruby on Rails、Next.js、categraf。

---

#### Apache License 2.0（SPDX: `Apache-2.0`）

| 许可                                                            | 条件                               | 限制                           |
| :-------------------------------------------------------------- | :--------------------------------- | :----------------------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 保留版权与许可声明<br>ⓘ 声明改动 | ✕ 责任<br>✕ 商标使用<br>✕ 担保 |

**一句话**：企业级首选的宽松许可证。除保留声明外，还要求**声明改动过的文件**；**明确授予专利权**，并带"专利报复"条款（若你对项目发起专利诉讼，你的专利授权自动终止）；明确排除商标权。

**关键兼容**：与 **GPLv2 不兼容**（专利终止条款被 GPLv2 视为"附加限制"），但 **与 GPLv3 兼容**。  
**适合**：企业开源、基金会项目、有专利布局的基础设施、需要明确专利条款的场景。  
**代表项目**：Kubernetes、Android、Apache 全家桶、Nightingale 夜莺、Spring Framework、TensorFlow。

---

#### BSD 2-Clause "Simplified" License（SPDX: `BSD-2-Clause`）

| 许可                                             | 条件                 | 限制             |
| :----------------------------------------------- | :------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 保留版权与许可声明 | ✕ 责任<br>✕ 担保 |

**一句话**：条款数量与 MIT 相当，只要求保留版权和许可声明。与 MIT 高度等价，常可互换使用。

**代表项目**：FreeBSD、libpcap、不少系统级工具。

---

#### BSD 3-Clause "New" or "Revised" License（SPDX: `BSD-3-Clause`）

| 许可                                             | 条件                 | 限制             |
| :----------------------------------------------- | :------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 保留版权与许可声明 | ✕ 责任<br>✕ 担保 |

**一句话**：在二条款基础上增加"**不得用原作者名义为衍生品背书/促销**"的条款，是最常用的 BSD 版本，与 MIT 兼容。

**代表项目**：Go 语言标准库部分代码、nginx、PostgreSQL。

---

#### BSD 4-Clause "Original" or "Old" License（SPDX: `BSD-4-Clause`）

| 许可                                             | 条件                 | 限制             |
| :----------------------------------------------- | :------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 保留版权与许可声明 | ✕ 责任<br>✕ 担保 |

**一句话**：带有臭名昭著的**广告条款**——所有宣传材料必须提及原作者。已极少使用，且**与 GPL 不兼容**，新项目应避免。

---

#### ISC License（SPDX: `ISC`）

| 许可                                             | 条件                 | 限制             |
| :----------------------------------------------- | :------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 保留版权与许可声明 | ✕ 责任<br>✕ 担保 |

**一句话**：功能与 MIT 几乎一致，但措辞更精简。适合喜欢"少即是多"的项目。

**代表项目**：OpenBSD、Node.js 早期版本、大量 npm 包。

---

#### Boost Software License 1.0（SPDX: `BSL-1.0`）

| 许可                                             | 条件                       | 限制             |
| :----------------------------------------------- | :------------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 保留声明（仅源码分发时） | ✕ 责任<br>✕ 担保 |

**一句话**：更宽松的"BSD/MIT 变体"，仅在**源码分发**时要求保留声明，二进制分发无需声明，对企业闭源集成极其友好。

**代表项目**：Boost C++ Libraries。

---

#### Mulan Permissive Software License v2（SPDX: `MulanPSL-2.0`）

| 许可                                                            | 条件                 | 限制             |
| :-------------------------------------------------------------- | :------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 保留版权与许可声明 | ✕ 责任<br>✕ 担保 |

**一句话**：中国团队主导、**OSI 认证**的中英双语宽松许可证。语义接近 MIT，但明确包含专利授权与商标排除，对国内项目更友好。

**适合**：希望使用中文法律文本、同时被国际认可的开源项目。  
**代表项目**：木兰开源社区、多款国产数据库/中间件。

### 4.2 公共领域 / 零条件

这类许可证连"保留署名"都不要，**最大程度放弃权利**。注意：企业项目若涉及专利/商标/著作人身权，使用前应咨询法务。

#### The Unlicense（SPDX: `Unlicense`）

| 许可                                             | 条件 | 限制             |
| :----------------------------------------------- | :--- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | —    | ✕ 责任<br>✕ 担保 |

**一句话**：明确将作品奉献给公共领域，放弃一切版权。OSI 批准。

---

#### Creative Commons Zero v1.0 Universal（SPDX: `CC0-1.0`）

| 许可                                             | 条件 | 限制             |
| :----------------------------------------------- | :--- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | —    | ✕ 责任<br>✕ 担保 |

**一句话**：CC 协议的公共领域奉献工具。更适合**数据、文档、图片**；软件也可用，但专利条款不如 Unlicense/0BSD 清晰。

---

#### BSD Zero Clause License（SPDX: `0BSD`）

| 许可                                             | 条件 | 限制             |
| :----------------------------------------------- | :--- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | —    | ✕ 责任<br>✕ 担保 |

**一句话**：零条款 BSD，连署名都不要，OSI 批准的极简许可证。

---

#### MIT No Attribution（SPDX: `MIT-0`）

| 许可                                             | 条件 | 限制             |
| :----------------------------------------------- | :--- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | —    | ✕ 责任<br>✕ 担保 |

**一句话**：MIT 去掉署名要求，适合内部工具或彻底"放手"的代码。

---

> ⚠️ **提醒**：WTFPL 虽然也是"想干嘛干嘛"风格，但法律措辞过于戏谑，不建议正式项目使用；选 0BSD / Unlicense / MIT-0 更稳妥。

---

### 4.3 弱 Copyleft（Weak Copyleft）

弱 copyleft 的折中思路：**被保护的代码本身不能闭源**，但允许它与闭源作品集成；LGPL 按"库"划分边界，MPL 按"文件"划分边界。

#### GNU Lesser General Public License v3（SPDX: `LGPL-3.0`）

| 许可                                                            | 条件                                                                     | 限制             |
| :-------------------------------------------------------------- | :----------------------------------------------------------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 公开源代码<br>ⓘ 保留版权与许可声明<br>ⓘ 相同许可证（库）<br>ⓘ 声明改动 | ✕ 责任<br>✕ 担保 |

**一句话**：GPL 的"库友好版"。**动态链接**调用 LGPL 库的闭源程序，上层无需开源；但**静态链接**时通常需提供可重链接的目标文件。

**边界**：LGPL 库自身的修改必须以 LGPL（或 GPLv3）发布；上层项目若只是调用接口，可保持闭源。

**适合**：基础库、运行时、希望被商业软件放心集成的组件。  
**代表项目**：Qt（部分版本）、GLib、FFmpeg（LGPL 配置）、GTK。

---

#### Mozilla Public License 2.0（SPDX: `MPL-2.0`）

| 许可                                                            | 条件                                                         | 限制                           |
| :-------------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 公开源代码<br>ⓘ 保留版权与许可声明<br>ⓘ 相同许可证（文件） | ✕ 责任<br>✕ 商标使用<br>✕ 担保 |

**一句话**：**文件级 copyleft**——被许可的单个文件及其修改必须以 MPL 发布；**新增的其他文件可闭源**，整体作品可用不同条款分发。MPL-2.0 还与 GPLv3 官方兼容。

**适合**：希望"核心代码不被私有化，但允许周边闭源集成"的项目。  
**代表项目**：Firefox、Thunderbird、Rust 编译器早期、部分 HashiCorp 项目。

---

#### Eclipse Public License 2.0（SPDX: `EPL-2.0`）

| 许可                                                            | 条件                                                         | 限制             |
| :-------------------------------------------------------------- | :----------------------------------------------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 公开源代码<br>ⓘ 保留版权与许可声明<br>ⓘ 相同许可证（文件） | ✕ 责任<br>✕ 担保 |

**一句话**：与 MPL 类似的文件级弱 copyleft，Eclipse 生态使用。**与 GPL 不兼容**，若要与 GPL 项目结合，通常需选 EPL-2.0 的 GPL 兼容次级条款。

**代表项目**：Eclipse IDE、Jakarta EE 部分项目。

---

### 4.4 强 Copyleft（Strong Copyleft）

强 copyleft 的核心：**只要包含/修改了该许可证的代码，整个衍生作品都必须以相同许可证开源，并提供完整源码。**

#### GNU General Public License v3（SPDX: `GPL-3.0`）

| 许可                                                            | 条件                                                               | 限制             |
| :-------------------------------------------------------------- | :----------------------------------------------------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 公开源代码<br>ⓘ 保留版权与许可声明<br>ⓘ 相同许可证<br>ⓘ 声明改动 | ✕ 责任<br>✕ 担保 |

**一句话**：最经典的强 copyleft 许可证。分发衍生作品时必须开源，并保留声明；明确授予专利权，禁止"tivoization"（用硬件锁死修改）。

**关键兼容**：与 Apache-2.0 **兼容**；与 GPLv2 **单向兼容**（GPLv3 代码不能并入 GPLv2 项目，除非项目标为 GPLv2-or-later）。  
**适合**：希望保护项目完整性、防止闭源分叉的核心基础设施。  
**代表项目**：Linux 内核（GPLv2）、GCC、Git、WordPress、OBS Studio。

---

#### GNU Affero General Public License v3（SPDX: `AGPL-3.0`）

| 许可                                                            | 条件                                                                                   | 限制             |
| :-------------------------------------------------------------- | :------------------------------------------------------------------------------------- | :--------------- |
| ✅ 商业使用<br>✅ 分发<br>✅ 修改<br>✅ 专利使用<br>✅ 私人使用 | ⓘ 公开源代码<br>ⓘ 保留版权与许可声明<br>ⓘ 网络使用即分发<br>ⓘ 相同许可证<br>ⓘ 声明改动 | ✕ 责任<br>✕ 担保 |

**一句话**：GPLv3 + **"网络使用即分发"**。只要用户通过网络与你的修改版交互，就必须提供源码。最强的 copyleft，对 SaaS 闭源有直接的"杀伤力"。

**适合**：服务器端项目、SaaS、不想被云厂商直接"白嫖"做托管服务的软件。  
**代表项目**：Grafana、Nextcloud、Mastodon、iText、MongoDB（改为 SSPL 之前）。

> **注意**：AGPL 的"网络使用即分发"只触发**源码提供义务**，并不禁止商业收费。很多 AGPL 项目采用"AGPL + 商业双许可"模式。

---

### 4.5 "源码可得"（Source Available）——不是开源

以下许可证**不符合 OSI 开源定义**（限制特定领域使用或特定商业模式），不应被称为开源许可证。使用前应逐条阅读全文。

#### Server Side Public License v1（SPDX: `SSPL-1.0`）

| 许可                                                     | 条件                                                                     | 限制             |
| :------------------------------------------------------- | :----------------------------------------------------------------------- | :--------------- |
| ✅ 商业使用（受限）<br>✅ 分发<br>✅ 修改<br>✅ 私人使用 | ⓘ 公开源代码<br>ⓘ 保留版权与许可声明<br>ⓘ 网络使用即分发<br>ⓘ 相同许可证 | ✕ 责任<br>✕ 担保 |

**一句话**：MongoDB 推出的"伪开源"许可证。若用 SSPL 软件提供托管/云服务，必须将整个服务栈（包括前后端、管理平台）全部以 SSPL 开源。OSI 明确声明**SSPL 不是开源许可证**。

**代表项目**：MongoDB、Elasticsearch、Kibana、Redis（可选 SSPL）。

---

#### Elastic License 2.0（SPDX: `Elastic-2.0`）

| 许可                   | 条件                                                     | 限制             |
| :--------------------- | :------------------------------------------------------- | :--------------- |
| ✅ 私人使用<br>✅ 修改 | 自定义：禁止作为托管服务提供<br>自定义：禁止绕过付费功能 | ✕ 责任<br>✕ 担保 |

**一句话**：Elastic 推出的**源码可得**商业许可证。允许查看、修改、内部使用，但**禁止以托管服务形式对外提供**，也禁止绕过付费功能。

**代表项目**：Elasticsearch、Kibana（8.x 起）。

---

#### Business Source License 1.1（SPDX: `BUSL-1.1`）

| 许可                          | 条件                                | 限制             |
| :---------------------------- | :---------------------------------- | :--------------- |
| 生产使用受限<br>开发/测试可用 | 约定若干年后自动转为宽松/开源许可证 | ✕ 责任<br>✕ 担保 |

**一句话**：HashiCorp 推出的"延迟开源"许可证。当前版本限制生产环境商业使用，约定 N 年后自动转为 MPL-2.0 等开源许可证。

**代表项目**：Terraform、Vault、Consul、Nomad（HashiCorp 全家桶）。

---

#### Redis Source Available License v2（SPDX: `RSALv2`）

| 许可         | 条件                      | 限制             |
| :----------- | :------------------------ | :--------------- |
| 商业使用受限 | 禁止与 Redis 商业产品竞争 | ✕ 责任<br>✕ 担保 |

**一句话**：Redis 7.4 起可选的源码可得许可证，限制将软件作为"数据库产品"与 Redis 竞争。

---

> ⚠️ **再次提醒**：在 MIT/Apache/BSD 等标准许可证后面**再加一句"禁止商用"**，不会让它变成有效的"限制版 MIT"。它只是一个自定义协议，既不受 OSI 认可，也缺乏法律先例。要么使用标准许可证，要么明确标注这是 Source Available 协议。

| 许可证                    | 类型        | 修改后可闭源         | 需公开源码范围 | 专利授权    | 网络交互触发 |
| ------------------------- | ----------- | -------------------- | -------------- | ----------- | ------------ |

## 五、决策树：五问定位法

阮一峰翻译自 Paul Bagwell 的经典决策树，用五个"是/否"问题定位：

```
                     开始
                       │
                       ▼
        他人修改源码后，是否可以闭源？
                       │
        ┌──────────────┴──────────────┐
        │ 是                          │ 否
        ▼                             ▼
每一个修改过的文件，            新增代码是否也要
是否都必须放置版权说明？        采用同样的许可证？
        │                             │
   ┌────┴────┐                  ┌─────┴─────┐
   │ 是      │ 否               │ 是        │ 否
   ▼         ▼                  ▼           ▼
Apache     MIT          ┌───────────┐  每一个修改过的文件，
License    License      │ 是否涉及  │  是否都必须放置版权说明？
                        │ 网络服务  │        │
                        │ (SaaS)？  │   ┌────┴────┐
                        └─────┬─────┘   │ 是      │ 否
                    ┌─────────┴────┐    ▼         ▼
                    │ 是           │ 否 MPL      LGPL
                    ▼              ▼  2.0
                 AGPL-3.0       GPL-3.0
```

### 第一步：三个核心问题（快猫星云提炼版）

1. **他人修改源码后，是否可以闭源？** —— 影响开源软件的商业化生态；
2. **新增的代码，是否要采用同样的许可证？** —— 即许可证的**传染性**，是项目不分叉的重要保障；
3. **每一个修改过的文件，是否都必须放置版权说明？** —— 版权归属问题。

### 第二步：两个补充问题

4. **衍生软件的广告，是否可以用你的名字促销？** —— 若"可以"，说明你几乎放弃了全部权利（→ MIT / 公共领域方向）；
5. **是否需要对源码的修改之处提供说明文档？** —— 对传染性的一种折中（→ Apache-2.0 / MPL 方向）。

### 三条一句话结论

| 你的诉求                                 | 选择           |
| ---------------------------------------- | -------------- |
| 期望项目真正、完全、不附加任何限制地开源 | **MIT**        |
| 期望保障项目完整性，不被分叉、不被闭源   | **GPL**        |
| 期望保留一定版权，又不限制他人商业化     | **Apache-2.0** |

### 面向具体场景的推荐

| 场景                           | 推荐                           | 理由                              |
| ------------------------------ | ------------------------------ | --------------------------------- |
| 个人随便写的小工具/插件        | MIT                            | 最省心，最易被接受                |
| 前端库 / npm 包                | MIT 或 ISC                     | 生态惯例，避免传染性吓退用户      |
| 公司开源的基础库               | Apache-2.0 或 MIT              | Apache 专利条款更利于企业法务过审 |
| 需要明确专利保护的基础设施     | Apache-2.0                     | 明确专利授权 + 专利报复条款       |
| 希望闭源商业软件也能用的库     | LGPL / MPL                     | 弱 copyleft 折中                  |
| 不希望被云厂商"白嫖"做托管服务 | AGPL-3.0                       | 网络使用即分发                    |
| 坚决不希望二次开发闭源         | GPL-3.0                        | 强 copyleft                       |
| 完全不在乎权利/数据文档        | Unlicense / CC0                | 贡献公共领域                      |
| 打算未来商业授权（双许可）     | AGPL / GPL + 商业许可          | 开源版受限，商业版获利            |
| 国内项目、需要中文法律文本     | MulanPSL-2.0                   | 中英双语 + OSI 认证               |
| 文档、书籍、图片、数据集       | CC-BY-4.0 / CC-BY-SA-4.0 / CC0 | **不要**用软件许可证给文档        |
| 硬件设计                       | CERN-OHL-P/W/S                 | 硬件专用                          |
| 字体                           | SIL OFL-1.1                    | 字体专用                          |

## 六、copyleft 的传染边界

这是最容易踩坑的地方，一张表说清：

| 使用方式                      | MIT/BSD/Apache (宽松式) | LGPL                     | MPL                       | GPL                         | AGPL                      |
| ----------------------------- | ----------------------- | ------------------------ | ------------------------- | --------------------------- | ------------------------- |
| 仅自己/公司内部使用（不分发） | 无义务                  | 无义务                   | 无义务                    | 无义务                      | 无义务                    |
| 完整复制源码分发              | 保留声明                | 保留声明 + 提供源码      | 保留声明 + 提供源码       | 保留声明 + 提供源码         | 保留声明 + 提供源码       |
| 修改源码后分发                | 保留声明即可（可闭源）  | 库本身须 LGPL 开源       | 修改的**文件**须 MPL 开源 | **整个作品**须 GPL 开源     | **整个作品**须 AGPL 开源  |
| 作为库**动态链接**调用        | 无影响                  | 上层可闭源               | 上层可闭源                | ⚠️ 争议，实践上通常认为衍生 | ⚠️ 争议                   |
| **静态链接**进自己的程序      | 无影响                  | 须提供可重链接的目标文件 | 无影响                    | 通常视为衍生 → 整体 GPL     | 通常视为衍生 → 整体 AGPL  |
| 直接**复制粘贴源码片段**      | 保留声明                | 该文件须 LGPL            | 该文件须 MPL              | 该文件须 GPL                | 该文件须 AGPL             |
| **SaaS / 网络服务**对外提供   | 无义务                  | 无义务                   | 无义务                    | **无义务**（不构成分发）    | ✅ **须提供修改后的源码** |
| 单纯调用远程 API / 命令行调用 | 无义务                  | 无义务                   | 无义务                    | 一般无义务（进程隔离）      | 一般无义务                |

> **关键点**：GPL 的传染发生在**衍生作品**层面。何为"衍生作品"在法律上有灰色地带（尤其是动态链接），没有法院定论。稳妥做法是：不确定时咨询法务，或直接用宽松式许可证的替代品。

## 七、选许可证还要考虑的现实因素

### 7.1 项目发起方视角

1. **商业模式**：靠什么赚钱？
   - 开源即营销（扩大采用） → 宽松式；
   - 双许可 / Open Core（开源版 + 商业版） → 强 copyleft 或 SSPL/BUSL；
   - 纯服务变现（不想被云厂商竞争） → AGPL 或 SSPL/BUSL。
2. **公司/组织政策**：很多公司有白名单（通常只允许 MIT/Apache-2.0/BSD 的入向依赖），出海/收购尽调时会查许可证清单。
3. **依赖的许可证**：你的许可证必须与依赖兼容（见第九节）。
4. **专利资产**：有专利布局 → Apache-2.0/GPLv3/MPL 等带专利条款的更合适。
5. **社区治理**：计划捐给基金会（CNCF/ASF/Linux Foundation） → 基金会通常要求 Apache-2.0 或指定许可证。
6. **变更成本**：**许可证变更很难**（需所有贡献者同意，或只在未来版本生效，且必然引发分叉风险）。

### 7.2 项目使用方视角（选型开源软件）

选开源项目时，许可证只是底线，还要综合看：

1. **生态位是否准确**：项目在开源链条上是否是关键一环，能否通过标准化输入输出嵌入生态。定位模糊、追求大而全、难以对接的项目往往发展受限。
2. **社区活跃度与多元化**：Issue 数量、PR 响应速度、Contributor 来源是否多元。
3. **许可证是否符合自身要求**：优先选 Apache/MIT/GPL 等主流许可证的项目；避开 SSPL/BUSL 等源码可得协议（商用前务必读条款）。
4. **是否有基金会托管**：基金会托管项目通常治理透明、不易随意变更许可证。

### 7.3 许可证变更的连锁反应

近年知名项目变更许可证（Redis、Elasticsearch、Kibana、Terraform、Grafana、Zabbix 等），无一例外都针对**商业使用**加限制：

- 对普通终端用户影响不大；
- 对**二次开发并商业化的公司**影响致命；
- 常引发**分叉与平替**：
  - Elasticsearch 改 SSPL → Amazon 分叉出 **OpenSearch**；
  - Redis 改许可证 → 微软推出平替 **Garnet**；
  - Terraform 改 BUSL → 社区分叉出 **OpenTofu**。

> **重要**：许可证变更通常**只对变更之后的版本生效**——你按旧许可证拿到的代码，权利不因上游变更而丧失（但该版本之后的新代码就没了）。MySQL 被 Oracle 收购后新版本改为商业许可证，旧 GPL 版本依然可以按 GPL 使用（MariaDB 就是这么分叉出来的）。

## 八、落地操作：从选到用

### 8.1 最小可行清单

| #   | 动作                          | 说明                                                                                                      |
| --- | ----------------------------- | --------------------------------------------------------------------------------------------------------- |
| 1   | 添加 `LICENSE` 文件（根目录） | **文件名必须叫 LICENSE 或 LICENSE.md**，GitHub/工具才能自动识别；放许可证全文，不要只写名字               |
| 2   | 填写版权行                    | `Copyright (c) 2026 Your Name`，年份可写成区间                                                            |
| 3   | 声明 SPDX 标识                | 源码头部注释 `SPDX-License-Identifier: MIT`，或在 `package.json` / `Cargo.toml` / `pyproject.toml` 里声明 |
| 4   | README 中说明                 | 加一节 "License"，写 "本项目采用 MIT 许可证，详见 LICENSE"                                                |
| 5   | 第三方依赖声明                | 若含第三方代码，加 `NOTICE` 或 `THIRD_PARTY_LICENSES` 文件                                                |
| 6   | 贡献协议                      | 明确 CLA 或 DCO（见 8.4）                                                                                 |
| 7   | 检查依赖许可证                | 跑一次许可证扫描，出 SBOM                                                                                 |

### 8.2 各生态的声明位置

| 生态       | 声明方式                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------- |
| npm        | `package.json` → `"license": "MIT"`（或 `"license": "(MIT OR Apache-2.0)"`）                 |
| Rust/Cargo | `Cargo.toml` → `license = "MIT"`                                                             |
| Python     | `pyproject.toml` → `license = {text = "MIT"}` 或 `license = "MIT"`；PEP 639 推荐 SPDX 表达式 |
| Go         | `go.mod` 无标准字段，靠 LICENSE 文件；用 `go-licenses` 检查依赖                              |
| Java/Maven | `pom.xml` → `<licenses>`                                                                     |
| 源码文件   | 文件头注释 `SPDX-License-Identifier: Apache-2.0`                                             |

### 8.3 常用 SPDX 标识速查

```
MIT              Apache-2.0         BSD-2-Clause       BSD-3-Clause
ISC              BSL-1.0            Unlicense          CC0-1.0
0BSD             MIT-0              MulanPSL-2.0       zlib
MPL-2.0          EPL-2.0            LGPL-2.1           LGPL-3.0
GPL-2.0-only     GPL-2.0-or-later   GPL-3.0-only       GPL-3.0-or-later
AGPL-3.0-only    AGPL-3.0-or-later  OFL-1.1            CC-BY-4.0
CC-BY-SA-4.0     SSPL-1.0           BUSL-1.1           LicenseRef-...（自定义）
```

### 8.4 贡献者协议：CLA vs DCO

| 方案                                       | 说明                                                                 | 适合                                                                                  |
| ------------------------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **DCO**（Developer Certificate of Origin） | 贡献者在 commit 里加 `Signed-off-by: Name <email>`，声明自己有权提交 | 轻量、社区友好，ASF/CNCF 部分项目用                                                   |
| **CLA**（Contributor License Agreement）   | 贡献者签署协议，授予项目方（或公司）使用/再许可的权利                | 需要**未来变更许可证**或**双许可商业化**的项目（Apache 基金会、Google、Microsoft 等） |

> 若项目未来可能改许可证或做商业授权，**必须**让贡献者签 CLA；否则你拿不到再许可的权利。


### 8.6 更换许可证的正确姿势

1. **已发布版本不可追溯修改**——旧版本用户仍按旧许可证持有权利；
2. 新增代码可换许可证，但**包含旧许可证代码的衍生作品**必须遵守旧许可证（除非兼容）；
3. 需要所有贡献者同意（这也是提前签 CLA 的意义）；
4. 发布公告说明生效版本与影响范围；
5. 心理准备：可能引发分叉。

## 九、许可证兼容性与依赖合规

### 9.1 常见兼容性结论

| 组合                             | 是否可行 | 说明                                                                      |
| -------------------------------- | -------- | ------------------------------------------------------------------------- |
| MIT / BSD / ISC 代码 → 任何项目  | ✅       | 宽松式几乎与所有许可证兼容                                                |
| MIT / BSD 代码 → GPL 项目        | ✅       | 单向兼容，合并后整体以 GPL 发布                                           |
| Apache-2.0 代码 → **GPLv2** 项目 | ❌       | 专利终止条款被视为附加限制                                                |
| Apache-2.0 代码 → **GPLv3** 项目 | ✅       | GPLv3 明确兼容 Apache-2.0                                                 |
| Apache-2.0 代码 → MIT 项目       | ⚠️       | 合并后需保留 Apache 的 NOTICE/专利条款，实践中通常整体改声明为 Apache-2.0 |
| GPL 代码 → MIT/闭源项目          | ❌       | 传染性不允许                                                              |
| LGPL 代码 → 闭源项目（动态链接） | ✅       | 但库本身修改须开源                                                        |
| MPL-2.0 代码 → GPL 项目          | ✅       | MPL 2.0 有官方 GPL 兼容条款                                               |
| EPL 代码 → GPL 项目              | ❌       | 不兼容                                                                    |
| AGPL 代码 → GPL 项目             | ❌       | AGPL 更强，合并后整体须 AGPL                                              |
| GPL 代码 → AGPL 项目             | ✅       | AGPL 向下兼容 GPLv3                                                       |
| BSD-4-Clause → GPL               | ❌       | 广告条款不兼容                                                            |

### 9.2 合规工具链

| 用途           | 工具                                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 依赖许可证扫描 | `pip-licenses`、`license-checker`(npm)、`cargo-deny`、`go-licenses`、`yarn licenses`                                                      |
| SBOM 生成      | Syft、CycloneDX、SPDX 工具链                                                                                                              |
| 深度合规审计   | FOSSology、ScanCode Toolkit、OSS Review Toolkit (ORT)                                                                                     |
| 在线查询       | [SPDX License List](https://spdx.org/licenses/)、[Choose a License](https://choosealicense.com/)、[TLDRLegal](https://www.tldrlegal.com/) |
| IDE/平台       | GitHub 依赖许可证洞察、GitLab License Compliance                                                                                          |

### 9.3 企业使用开源软件的合规动作

1. 建立**入向许可证白名单**（如：允许 MIT/Apache-2.0/BSD/ISC，GPL/AGPL 需审批）；
2. 在 CI 中集成许可证扫描，阻断黑名单依赖；
3. 生成并归档 SBOM（客户尽调/IPO 尽调会要）；
4. **分发产品**时履行披露义务：附 `THIRD_PARTY_LICENSES`、提供 copyleft 代码源码获取方式；
5. 注意：AGPL 依赖若用于对外服务，需评估源码披露义务。

## 十、常见误区与 FAQ

### 误区 1："代码放 GitHub 上就是开源了"

错。没有 LICENSE = 保留全部版权。

### 误区 2："GPL 病毒，用了就必须全部开源"

- 只有**分发衍生作品**时才触发；
- 自己用、公司内部用、SaaS（GPL 非 AGPL）都不触发；
- 实际上违反 GPL 的法律救济是"停止侵害 + 赔偿损失"，法院一般不会强制你开源源码，只会判你停止使用。

### 误区 3："MIT 是最宽松的，所以最安全"

MIT 对**使用者**最自由，但对**作者**放弃最多（无专利条款、无改动声明要求）。有专利风险或需保留权利时，Apache-2.0 更稳妥。

### 误区 4："我用 MIT，再加一句禁止商用就行"

不行。这构成了非标准的自定义协议，不再满足开源定义，且"MIT + 附加限制"的措辞在法律上容易产生歧义。要么用标准许可证，要么明确标注为 Source Available。

### 误区 5："改个许可证名字/缩写就是另一个协议"

不是。只有**许可证全文**才是法律文本。BSD-2/3/4 发音一样，条款差很多。

### 误区 6："开源软件不能卖钱"

错。绝大多数开源许可证（含 GPL）**允许商业使用和销售**，限制的是"闭源"和"不提供源码"。GPL 软件完全可以标价出售，只是必须同时提供源码并允许转售。

### FAQ

**Q1：MIT、GPL、Apache 优先记住哪几个差异？**
MIT 更宽松；GPL 强调衍生作品继续开源；Apache 对版权与专利授权表达更完整。非法律专业人士掌握这三类即可覆盖大量场景。

**Q2：开源软件的专利怎么处理？**
Apache-2.0 和 GPLv3 含明确专利授权；BSD、MIT、GPLv2 未提及专利，但一般认为默认隐含授予。除非有明确的"保留专利"条款，使用开源软件通常不构成专利侵权。

**Q3：什么叫披露要求（notice requirement）？**
所有开源许可证都要求分发者告知用户"软件里含有开源代码"。通常做法是：提供完整的原始许可证文本 + 披露原始作者。

**Q4：文档/图片/数据用什么许可证？**
用 **Creative Commons** 系列（CC-BY-4.0 / CC-BY-SA-4.0 / CC0），不要套用软件许可证。反过来也一样：代码不要用 CC 许可证（CC 没有专利条款、ND/NC 条款也不适合代码）。

**Q5：项目里有 GPL 依赖，我还能闭源吗？**
通常不能（若构成衍生作品）。解决方案：换成 MIT/Apache 的替代品，或联系作者购买商业授权（很多 GPL 项目提供双许可）。

**Q6：怎么快速判断一个陌生许可证？**
查 [SPDX License List](https://spdx.org/licenses/) 或 [TLDRLegal](https://www.tldrlegal.com/)，看它的 permissions / conditions / limitations 三段。

**Q7：双许可是怎么回事？**
同一份代码同时以"开源许可证（通常是 AGPL/GPL）+ 商业许可证"提供。想闭源的客户付费买商业许可。这是 GNU 时代就有的经典商业模式（MySQL、Qt、iText、MongoDB 早期）。

**Q8：我用 GPL 项目做 SaaS，要开源吗？**
GPL v2/v3：**不需要**（SaaS 不构成分发）。AGPL：**需要**。

### 三、按「传染性强度」排序速查

| 强度           | 许可证                                 | 一句话边界                              |
| -------------- | -------------------------------------- | --------------------------------------- |
| 0 无条件       | Unlicense / CC0 / 0BSD / MIT-0 / WTFPL | 连署名都不必保留                        |
| 1 最弱         | MIT / BSD / ISC                        | 仅需保留版权声明                        |
| 2 弱（含专利） | Apache-2.0 / MulanPSL-2.0              | 保留声明 + 声明改动 + 明确专利          |
| 3 文件/库级    | LGPL / MPL / EPL / MS-RL               | 被许可的文件或库须开源，外层可闭源      |
| 4 项目级       | GPL-2.0 / GPL-3.0                      | 整个衍生作品必须 GPL 开源               |
| 5 最强         | AGPL-3.0                               | 增加「网络使用即分发」，SaaS 也必须开源 |
| — 非开源       | SSPL / BUSL / Elastic / RSAL           | 限制商用/托管，不满足 OSI 开源定义      |

### 四、常用「条件」列释义

| 条件                          | 含义                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------- |
| 公开源码（Disclose Source）   | 分发被许可材料时，必须提供其源代码                                              |
| 保留声明（Notice）            | 分发时必须随附许可证与版权声明副本；BSL 仅源码分发时需保留                      |
| 相同许可证（Same License）    | 修改后的作品须以相同许可证发布；ⓘ库=库级、ⓘ文件=文件级                          |
| 网络使用即分发（Network Use） | 通过网络与软件交互的用户，有权获得源码副本（AGPL / SSPL）                       |
| 声明改动（State Changes）     | 须记录对源文件的修改（Apache-2.0、GPL 系列、EPL 等）                            |
| 专利使用（Patent）            | ✓ = 许可证明确授予贡献者专利；— = 未提及（通常视为隐含）；✕ = 显式不授予（CC0） |
